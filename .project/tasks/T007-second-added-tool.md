# T007 — Add the error_digest_lookup tool in a second commit that touches no envelope file

## Context

The second addition is what turns T006's pin into a proof: two separate commits, the registry core
byte-identical between them, and no shared module edited except the provider list. This task adds
`error_digest_lookup`, a real read over the error digest the extension already ships
(`src/main-world/error-digest.ts`, 61 577 B with 64 entries, statically imported by
`error-explainer.component.ts:7` and therefore already inside `main.js`), so the tool costs the
initial bundle nothing it does not already pay. It must obey the digest's own rule: the bundled MIT
and Google LLC notice is stripped from every entry before any text leaves the module.

## Approach

- Read `src/main-world/error-digest.ts` and `src/main-world/error-capture.ts` before writing, plus
  T006's pin. Do not edit `tool-registry.ts`, `page-reads.ts`, `read-tools.ts`, `app-facts.ts`,
  `hostile-tools.ts` or `panel-environment.tool.ts`: this commit adds one module, its spec and one
  provider line.
- `error_digest_lookup` is a `read` on `['panel']` with `outcome: 'result'` and `publish: 'model'`;
  its input schema takes one required `code` string. It reads the digest module — not
  `extension/error-digest.json` (that file is `generate-error-digest`'s output and is regenerated by
  the build; do not write it, and do not run that target).
- Normalise the code before lookup: trim, upper-case the `NG` prefix, accept both the `NG0####` and
  bare `####` forms, and reject anything that is not a four-to-five digit code with
  `{ kind: 'error', code: 'invalid-input' }` naming the tool. An unknown but well-formed code returns
  `{ kind: 'error', code: 'invalid-input' }` naming the tool and the code — never an empty `result`
  and never a guess at the nearest entry.
- Strip the bundled licence notice from the returned text. The project's digest decision is that the
  MIT and Google LLC notice stays on the shipped file and never reaches the model, so the tool returns
  entry text with the notice removed; a returned string that still contains the notice is a defect.
  Return the code, the title and the body, with `provenance: 'panel'`.
- Do not add a second copy of the digest, a second lookup table, or a fetch. The module imports the
  existing digest and maps it.
- The provider line `provideErrorDigestTool()` is the only edit `app.config.ts` receives; no
  `*.component.ts` change (INTENT Scope: out) and no DOM added anywhere (AR-3).
- The spec proves the second addition did not disturb the first: register every cohort that exists at
  this commit in one TestBed, snapshot each declaration's `id`, `kind`, `host`, `outcome` and
  `publish`, and assert the earlier cohorts' snapshots match the fields they declare today. It also
  asserts the looked-up entry deep-equals the entry the shipped error explainer reads from the same
  module, so the tool cannot drift into a private copy.
- Keep the module dependency-free beyond `@angular/core` and the digest module (AR-1: ~13.7 KiB of
  headroom against 520 KB).
- Measured at this head: `--include` takes a workspace-relative path and may be repeated.

## Interface contract

- `ToolKind = 'read' | 'write' | 'confirm'`; `ToolHost = 'page' | 'iframe' | 'panel' | 'worker' | 'extension-API' | 'tester'`; `ToolOutcomeKind = 'result' | 'confirm-required' | 'async-handle' | 'image' | 'error'`; `ToolPublish = 'model' | 'panel' | 'internal'`; `ToolProvenance = 'panel' | 'page-published' | 'page-request' | 'third-party'`; `ToolErrorCode = 'not-implemented' | 'declaration-invalid' | 'invalid-input' | 'host-unavailable' | 'third-party-failed'`.
- `ToolFacts = Readonly<Record<string, unknown>>`; `ToolInputSchema = { readonly type: 'object'; readonly properties: Readonly<Record<string, { readonly type: 'string' | 'number' | 'boolean' | 'object' | 'array'; readonly description?: string; readonly enum?: readonly string[] }>>; readonly required: readonly string[] }`.
- `ToolDeclaration = { readonly id: string; readonly title: string; readonly kind: ToolKind; readonly host: readonly ToolHost[]; readonly outcome: ToolOutcomeKind; readonly publish: ToolPublish; readonly input: ToolInputSchema | ((facts: ToolFacts) => ToolInputSchema) }`.
- `ToolOutcome = { readonly kind: 'result'; readonly value: unknown; readonly provenance: ToolProvenance } | { readonly kind: 'confirm-required'; readonly token: string; readonly summary: string } | { readonly kind: 'async-handle'; readonly handle: string } | { readonly kind: 'image'; readonly mimeType: string; readonly dataUrl: string; readonly provenance: ToolProvenance } | { readonly kind: 'error'; readonly code: ToolErrorCode; readonly toolId: string; readonly message: string }`.
- `ToolContext = { readonly facts: ToolFacts; readonly provenance: ToolProvenance }`; `ToolBacking = { readonly execute: (input: unknown, context: ToolContext) => Promise<ToolOutcome> }`.
- `ToolRegistry = { readonly tools: Signal<readonly ToolDeclaration[]>; declare(declaration: ToolDeclaration): void; attach(toolId: string, backing: ToolBacking): void; execute(toolId: string, input?: unknown, context?: ToolContext): Promise<ToolOutcome>; awaitHandle(handle: string): Promise<ToolOutcome> }`, provided under the `TOOL_REGISTRY` `InjectionToken<ToolRegistry>`; `awaitHandle` answers `{ kind: 'async-handle', handle }` while the handle is pending.
- `ToolDeclarationError extends Error` carries `readonly toolId: string` and `readonly field: 'id' | 'kind' | 'host' | 'outcome' | 'publish' | 'input'`; its message contains both values.
- `defineTool(declaration: ToolDeclaration, backing: ToolBacking): ToolEntry` and `provideTools(...entries: readonly ToolEntry[]): EnvironmentProviders` are the authoring surface; every tool module registers through them and edits nothing inside `tool-registry.ts`. `provideToolRegistry(): EnvironmentProviders` provides `TOOL_REGISTRY`.
