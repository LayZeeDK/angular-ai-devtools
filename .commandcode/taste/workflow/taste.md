# Workflow preferences

- Pair every tool, fixture or runtime the project adopts with a `control-{name}` skill and a `verify-{name}` skill, keep them maintained, and consult/use them for controlling and verifying those tools (including feature-flagged browser capabilities such as Edge's Prompt API). He asked for this pair for AI browsers (Chrome Beta / Edge Dev), the Angular dev-app fixtures, Angular DevTools, Pangular Inspector, Vitest Browser and SSR support; use `control-*`/`verify-*` skills, `/lars-verify`, and `/lars-maintain-verification` where applicable. Confidence: 0.95
- Works through his own slash commands (`/lars-mode`, `/poteto-mode`, `/lars-frontend-dev`, `/lars-create-verification`, `/lars-maintain-verification`, `/lars-verify`, `/pstack:create-verification-skill`, `/pstack:maintain-verification-skill`): the expected output of a piece of work is a skill, playbook or research file, not an ad-hoc script. Confidence: 0.8
- Preserves local git remotes/backups (e.g. `D:/projects/sandbox/.angular-ai-devtools.git`) and does not destroy them during cleanup. Confidence: 0.85
- Prefers real (non-mocked) recorders and authentic cycle data in browser/integration tests of the DevTools panel rather than fabricated or mocked chain data. Confidence: 0.7
- Prefers end-to-end verification in a real browser (Chrome/Edge) over unit-test-only verification for web-facing features. Confidence: 0.85
- Do not assume prerequisites (browser feature flags, model downloads, remote-debugging permissions, app state). Confirm them, enable them himself-free when possible, and escalate to him only when the agent genuinely cannot. When there is a manual/seed path, perform the steps himself rather than handing instructions to the user. Confidence: 0.95
- When he has prior successful runs of a capability, does not accept a conclusion that it is impossible in the current environment; expects mitigations and bootstrap steps (flags, component downloads) to be researched and attempted instead. Confidence: 0.75
- Research the web and prior art instead of relying on assumptions: he asks "did you research on the web whether ...", asks for cloud-AI/MCP/WebMCP prior art to be mined so it can be re-expressed with browser built-in AI, points at changelogs, releases and third-party sites as sources, and asks for further independent benchmarks and head-to-head comparisons when the first pass rests on one source; when a capability is blocked or unsupported, he also asks to research mitigations on the web and GitHub (e.g. Chromium issue tracker). Confidence: 0.75
- Do not start Fable subagents on his behalf without asking; if a task fits Fable, ask first, or use Opus during AFK/overnight runs. Confidence: 0.85
- Long autonomous runs are normal (AFK/overnight lars-mode): during such runs the agent should make all decisions (including values calls) autonomously without deferring to humans (defer no decisions to a human), stopping only on hard constraints or errors, and the run should end with a plain what's-done / what's-left report. Confidence: 0.85
- Work stays uncommitted and unpushed unless he asks to commit; upstream findings go into a filing ledger as drafts, never filed. Confidence: 0.7
- Prefers atomic, bisect-safe Conventional Commits: each change set is one focused commit that leaves the repo in a working state suitable for `git bisect`, and follows the Conventional Commits format (e.g. `feat:`, `fix:`, `chore:`). Confidence: 0.9
- Project-local config generated by tools (e.g. `.commandcode/settings.json`) should be committed to the repo rather than gitignored or kept machine-local — once confirmed to hold no tokens or machine-specific paths. Confidence: 0.6
- Commit taste-file (`taste.md`) changes automatically whenever they are detected — but always in their own dedicated commits, never bundled with code or with other taste files (one commit per changed taste file). Confidence: 0.95
- Splits config into shared vs personal layers: shared project settings stay committed in `.commandcode/settings.json`, while personal/machine-specific config such as permission rules goes in a gitignored `.commandcode/settings.local.json`. Confidence: 0.7
- Allows all `git` commands without prompting, but `git push` must always stay at "ask" (never auto-approved). Confidence: 0.75
- Writes commit messages to temp files via the `write_file` tool and commits with `git commit -F <path>` when heredocs are unavailable in the shell (e.g. Windows cmd), rather than attempting inline `git commit -F - <<'EOF'` syntax. Confidence: 0.8
- Reviews `.commandcode/taste/` changes with `git diff` before committing taste files, to verify the recorded preferences match the session's learnings. Confidence: 0.7
- Organizes agent instructions/rules with progressive disclosure: a compact root file (CLAUDE.md / AGENTS.md) that points to a `references/*.md` folder read on demand, rather than one large file. Confidence: 0.8
- Shapes well-scoped work items with guardrails, clear goals, and expected outcomes for faster free models to execute, then reviews their output (via Laguna S 2.1 and/or Ornith) rather than doing the work in the main thread — prioritizing speed while keeping review in-house. Confidence: 0.9
- Delegates substantial, multi-part work to subagents (e.g. one research subagent per model) instead of doing everything in the main thread. Confidence: 0.85
- Prefers using free subagents for parallelizable scanning/summarization tasks (e.g. summarizing a prior session that failed to auto-compact, then resuming its work) rather than doing the scanning inline; treats subagent delegation as the default mechanism for this class of work. Confidence: 0.75
- Orchestrates multi-part work as a chunked pipeline: chunks the work across multiple parallel subagents, then routes a dedicated synthesis subagent to combine their outputs rather than synthesizing in the main context, keeping its own context lean. Confidence: 0.85
- Keep scope narrow to exactly what was asked: when adapting/mirroring an existing setup (e.g. porting the Claude config to Command Code), carry over only the directly relevant parts, not the whole thing or unrelated sections and conventions. Confidence: 0.6
- Follows existing code conventions and patterns when creating new scripts (e.g. "similar to the other install-*.mjs scripts in scripts/"). Confidence: 0.85
- Uses a plan-first workflow: writes implementation plans to `~/.commandcode/plans/`, presents them via `exit_plan_mode`, and waits for approval before implementing. Confidence: 0.75
- Creates new skills by analyzing the difference between existing parallel skills (e.g. create-vs-maintain variants of the same skill type) and applying the same transformation pattern to generate new skill variants. Confidence: 0.8
- Skill-install scripts are self-managing across their lifecycle via flags: `--dry-run` (preview without writing), `--no-pull` (reuse existing clone without fetching), `--uninstall` (remove installed skills + manifest), `--clean-cache` (remove the temp clone), and `--quiet` (suppress output). Confidence: 0.75
- Treats "create and test" as a single integrated workflow step — newly created skills must be tested as part of their creation, producing verified working versions rather than untested artifacts. Confidence: 0.75
- When a background subagent exhausts its capacity mid-task (token limit hit partway through), recovers by splitting the remaining work into smaller per-group subagents — one subagent per logical group — rather than retrying the same monolithic prompt, reading the input inventory first to find natural grouping boundaries. Confidence: 0.75
- Batches audit-subagent work at 2–3 docs per subagent (not 5+ like the original monolithic groups) to stay within the ~500s–1100s reliability window before mid-run 429 crashes; larger groups fail far more often. Confidence: 0.85
- Scopes every audit subagent to read ONLY the target docs plus an explicit enumeration of source roots (.claude/skills/_/scripts/, .commandcode/skills/_/scripts/, spikes/, docs/, plans/, research/), with a hard denylist of AGENTS.md, role briefs/templates/brief files/.project/, git commands, and alignment mode — keeping the context minimal and focused. Confidence: 0.9
- Collates parallel subagent partial outputs into a single template-compliant deliverable and validates it programmatically (check_docs_audit.py: disjoint ## Doc: / ## Descriptive docs sections matching the frozen inventory, consistent summary counts, and a populated remediation queue) before the finish-inspect gate (--expected-head, --inspection, --mapper-reviewed). Confidence: 0.8
- When porting or adapting a skill from one tool ecosystem to another (e.g. Claude → Command Code), first research the target tool's conventions — especially frontmatter metadata and tool syntax — then adapt; do not copy verbatim, and if a verbatim copy was made, remove it and regenerate via the target tool's creation workflow (e.g. `/lars-create-verification`) instead. Manual copy-and-path-adapt, even if tests pass, is not an acceptable substitute and he will ask whether the dedicated creation workflow was used. When asked to start from scratch, remove copied/adapted artifacts first and regenerate rather than patching copies, even if the existing artifacts currently pass tests. Confidence: 0.98
- Replace (remove) superseded skill families when a newer equivalent is adopted rather than keeping both — e.g. drop `lars-create-control-skill`/`lars-maintain-control-skills` in favour of the `lars-create-verification`/`lars-maintain-verification`/`lars-verify` set. Confidence: 0.8
- Apply the Cat Jam and Laguna S 2.1 prompt guidelines from `~/.commandcode/references/prompting-*.md` to Command Code skills (a short "Prompting (Cat Jam/Laguna S 2.1): …" note in each skill). Confidence: 0.9
- Prefers blind/independent review of skill artifacts: reviewers are scoped to the target skill's own files plus the relevant prompting guidance and must evaluate it on its own content, without knowledge of counterpart/source skills or other background context. Before a deeper second review round, performs additional research using official tool docs/knowledge skills (not only installed references) and shares the resulting rules with the reviewers; chooses the reviewer effort level to match the round's depth, escalating to higher-effort reviewers for deeper rounds. Confidence: 0.8
- Prefers no AI co-author attribution trailer on commits: sets `attribution.commit` to an empty string, preferring the global `~/.commandcode/settings.json` over project-local config when possible. Confidence: 0.85
