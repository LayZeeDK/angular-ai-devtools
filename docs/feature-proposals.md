# AI-assisted Angular DevTools: feature proposals

Date: 2026-10-11, updated 2026-10-12. Author: Claude, for Lars. Status: research and design, nothing built.

Target: a Chrome and Edge MV3 extension that inspects any Angular 22.2 application running in development mode and answers questions about it with the browser's built-in on-device model. Lars accepted Chrome Beta or Edge Dev as a prerequisite browser.

## 1. Summary

**Supported apps.** Angular 22.2 in development mode, bootstrapped standalone, with zoneless change detection, functional APIs (functional guards, resolvers, interceptors and providers such as `provideRouter`), and Signal Forms (Lars's ruling of 2026-10-12, section 8). Everything else is unsupported, and the design has no second code path for it:
- A Zone.js app gets a "not supported" notice in the panel instead of a chat. The panel decides this with the zone-mode check in `app_facts` (3.3, 3.4). An app that is zoneless but still loads zone.js is supported; N10 flags the leftover polyfill.
- NgModule apps are unsupported. This includes the `RouterModule.forRoot` router setup, which publishes no router globals **[measured, 02 section 1.1]**. The panel has no check that detects an NgModule bootstrap; none was looked for in the evidence (section 9).
- Template-driven and Reactive Forms are unsupported; the forms feature (N15) reads Signal Forms only.

No shipped framework devtools panel uses an on-device model **[inferred from search, 03 section 5]**. Pangular Inspector, Chrome DevTools for agents, agent-react-devtools and the Angular CLI MCP server all hand data to an external cloud or IDE agent; Chrome's own DevTools assistant runs on cloud Gemini and is opt-in under terms of service.

The Angular AI docs contributed five things:
- `overview.md` (the "Build with AI" page at `angular.dev/ai`) is about apps that call cloud models. Its best practices match 3.3 and 3.5: tools that the developer controls, a human in the loop (3.5's confirm before writes), and output constrained by a schema **[documented, Angular AI docs read in 02 section 4.1]**.
- `design-patterns.md` gives one of N2's rules.
- WebMCP support gives N9.
- The Angular CLI MCP server is the code-side complement to this extension (N13).
- `agent-skills.md` names the `angular/skills` repo, which is the rule source for N10 **[documented, 02 section 4.5; rules counted in 06]**.

The AI tutor (`ai-tutor.md`) is a persona for a coding agent. It runs through the CLI MCP server and reads project files **[documented, Angular AI docs read in 02 section 4.4]**. So it has no runtime counterpart in a devtools extension **[inferred]**.

Four facts shape the design:

1. **On-device models can drive tools today, but not equally.**
   - Aion-1.1-Instruct (Edge Dev 157) answered all 15 benchmark runs through native tool calls, at 3-6 s per question.
   - Gemma 4 (Chrome Beta 156) is reliable only through a structured-output loop (13/15 runs on the default GPU low tier, 15/15 on CPU, which needs the `OnDeviceModelForceCpuBackend` command-line feature).
   - Gemini Nano also runs on that loop, because in native mode it makes no tool calls at all. On the loop it passed 11/15 runs on GPU and 0/15 on CPU, so it is supported on GPU but not reliable, and unsupported on CPU.
   - Phi-4-mini (Edge stable) is weak at both **[measured, 05; Nano GPU figures regraded with `916fc09`, `spikes/probes/regrade.mjs`]**.
   - The browser never runs tools itself: `prompt()` returns `tool-call` parts, and the extension runs them and sends `tool-response` parts back **[measured, 00 and 01]**.
   - So the extension needs a routing rule. No API in the evidence names the model, so the rule in 3.3 uses what the extension can observe: native tools only on Edge with a `contextWindow` of 7,168 (Aion as measured) and a passing native canary; the structured-output loop everywhere else; unsupported when the structured-output canary fails. It is a heuristic, with a manual override in the panel settings **[inferred from measured per-model results]**. `availability()` cannot tell whether tools work **[measured, 09]**.
2. **The context window is small: 7,168 tokens on Aion and 9,216 on the Chrome models and Phi-4-mini** **[measured, 05]**. A whole page's component details and signal graphs do not fit (05 S3); a bare component list does. The model gets facts by id from small tools that return a short summary; it never receives full output.
3. **Angular 22 already ships two in-page AI tools.** Every dev-mode app answers the `devtoolstooldiscovery` DOM event with `angular:di_graph` and `angular:signal_graph` **[measured, `packages/core/src/debug/ai/registration.ts:21-38`, `platform.ts:48-50`]**. The extension can collect them with one event dispatch and no `ɵ` name (run from the page's main world in S2; from the extension's content script, spike S8). The design uses them only in part: 3.2 never runs `angular:di_graph`, and for the signal graph it either wraps `angular:signal_graph` behind a component id or calls `ng.ɵgetSignalGraph` directly.
4. **Most of what Angular DevTools shows is reachable from `window.ng` in a MAIN-world script** with no app change **[measured, 02 section 1-2]**. The parts that need internals are already on the page in dev mode, mostly as `ng.ɵ*` functions (Tier 1). Real Tier 2 gaps at 22.2 are small: `@if`/`@switch` block state, template local refs, the DI event stream **[measured, 02 section 1.3 and 5.7]**, and error-boundary state **[inferred from absence: no boundary hook in `global_utils.ts` or `control_flow_types.ts`, 02 section 5.6]**. The error-boundary gap means that `ng` exposes no boundary API. N16 tries a Tier 0 route around it, which its spike must confirm.

Recommended first release, in priority order:

| # | Feature | Why it is new | Tier |
|---|---|---|---|
| N1 | "Why did this update?" change-detection causality | Angular DevTools shows timings; it does not follow the chain through signals to each component. In a zoneless app that signal chain is the only record of what caused the cycle | 1, depends on Decision 1 |
| N2 | Signal provenance and reactive anti-pattern finder | The signal graph pane draws nodes; it does not trace or judge | 1, depends on Decision 1 |
| N3 | DI doctor | Explains resolution failures and duplicate instances in prose | 0 + 1, depends on Decision 1 |
| N4 | Angular error explainer | On-device Console Insights that knows `NG0xxx` and the owning component | 0 |
| N6 | Capture-to-test (Vitest Browser Mode) | Turns live state into a runnable spec | 0 (+ 1 for the import path) |

N1, N2 and N3 use Tier 1 (`ng.ɵ*` functions already on the page), and so does N6 for its import path. The brief asks to avoid Tier 1. Lars ruled on Decision 1 in section 8 on 2026-10-12: Tier 1 is allowed, labelled and feature-detected. The Tier 0-only first release listed under Decision 1, led by N4, N6, N10's Tier 0 rules and N11, stays there for the record.

Stretch (app opt-in): N9, agent rehearsal for WebMCP tools. It tests whether a small model can use the app's own tools, so it works only on apps that register WebMCP tools. The brief calls that a stretch: "using WebMCP in the Angular application may be considered a stretch prerequisite".

Plus a chat panel that promptifies every Angular DevTools tab (section 5), and ecosystem adapters led by an NgRx Redux DevTools shim (section 6).

API details that the implementation must follow **[measured, 00 and 01]**:

- `create()` with `tools` needs both `expectedOutputs: [{type:'text'}, {type:'tool-call'}]` and `expectedInputs: [{type:'text'}, {type:'tool-response'}]`, or it throws.
- Tool calls arrive as `LanguageModelToolCall` objects with getter fields `name`, `callID`, `arguments`. `JSON.stringify` shows `{}`. The member is spelled `callID`; `callId` throws.
- Results go back as `new LanguageModelToolSuccess({callID, name, result: [{type:'object', value}]})` (or `LanguageModelToolError`) inside `{role:'user', content:[{type:'tool-response', value}]}`, immediately after the call. Prompting without a response fails with `kErrorUnknown`.
- Model quirks to code around:
  - Gemma 4 returns `callID: ""`. Pass it back unchanged.
  - Gemma 4 fails tool prompts with `kErrorUnknown` on camelCase tool names without underscores such as `getComponentCount`, while `get_component_count` works **[measured, S1 phase 2, 11]**. The rename changed case and underscores together, and the two were not separated (11; spike S11).
    - Answered (2026-10-12, S11): an uppercase letter in the tool name is what fails. On the Gemma 4 instance (Chrome Beta 156.0.8078.17, GPU low tier), one fresh session per variant, 70 s apart: `get_component_count` with a required `scope` returned a tool call with `{"scope":"page"}`; `get_component_count` with empty `properties` returned a tool call with `{}`; `getcomponentcount` (lowercase, no separator) returned a tool call with `{"scope":"page"}`; `getComponentCount` and `Get_component_count` failed with `kErrorUnknown` **[measured, n=1 per variant, `research/raw/tool-name-matrix-gemma4-gpu.json`]**. So missing underscores do not fail, and an empty `properties` schema does not fail **[measured, n=1 per variant; inferred that it generalises]**. A doctor run right after passed every canary, so the two crashes did not disable the model **[measured]**. Gemma 4 on CPU, Nano, Aion and Phi-4-mini were not run on the matrix.
  - Chrome disables the on-device model after three crashes without a successful response in between; a successful response resets Chrome's count **[measured, Chromium 156 source, 11]**. On Gemma 4, the camelCase `kErrorUnknown` failures were model-process crashes **[measured, 11]**; that the two S11 failures were crashes too is **[inferred: same error on the same instance]**. Chrome re-enables the model after 1 minute at the third crash, and the wait doubles per further crash, up to 1 hour **[measured, Chromium 156 source, 11]**.
  - Whether other `kErrorUnknown` errors count toward that limit is **[inferred]**, not checked. The same code also comes back in cases with no camelCase name:
    - for a prompt sent after an unanswered tool call (Aion, 00);
    - in Edge benchmark runs (Aion fallback 1, Phi-4-mini 3), where Chromium's crash counter is not known to apply;
    - once on Gemma 4 in Chrome Beta, with snake_case tool names and a required parameter on every tool (native, question 4, run 2: `ERR UnknownError: An unknown error occurred: kErrorUnknown`, `calls: []`) **[measured, `research/raw/bench/gemma4.json`; tool schemas at `spikes/probes/bench.js:56-58`]**. That browser is the one whose crash counter disables the model, so if this error was a crash, it counted toward the limit **[inferred]**.
  - The earlier finding that empty `properties` causes the failure is confounded, because every failing probe also used camelCase names **[measured, 11]**. The controlled test (`spikes/probes/tool-name-matrix.js`) was stopped by a low-memory shutdown and has not run.
    - Answered (2026-10-12, S11): the test ran, and the empty-schema suspect is cleared for Gemma 4 on the GPU low tier: a snake_case tool with empty `properties` returned a tool call **[measured, n=1, `research/raw/tool-name-matrix-gemma4-gpu.json`]**. Aion accepted an empty schema earlier **[measured, 00]**.
  - Until that test runs, tools use snake_case names and at least one parameter (a required `scope` or `id`). That rule avoids the two known suspects, not every crash: the Gemma 4 run above followed it and still failed **[inferred]**. The rule for what the extension does after a `kErrorUnknown` on Chrome is in 3.3.
    - Answered (2026-10-12, S11): the rule is now: tool names are lowercase (snake_case recommended for readability). The rule of at least one required parameter is relaxed: a tool with nothing to ask may take an empty `properties` schema. No other reason for the dummy parameter was found: it existed only for the empty-schema suspect, no run measured it helping argument accuracy, and it adds an argument the model can fill wrongly, as Aion did in S1 phase 2 (`scope: "app-counter"`, 11) **[measured, 11; the relaxation is inferred design]**. The native canary keeps its parameter for a different reason (3.3). The lowercase rule avoids the measured trigger, not every crash: the snake_case Gemma 4 benchmark failure above still stands **[measured, `research/raw/bench/gemma4.json`]**.
  - Streaming on Gemma 4 tool sessions is not established either way. The only test (`spikes/probes/probe9.js:18-27`) called `prompt()`, got a tool call back, and then streamed on a `clone()` of that session without sending a `tool-response`. That failed with `kErrorUnknown` **[measured, 00]**, but a prompt after an unanswered tool call fails on its own (above), so the test does not show that streaming fails. Spike S7 streams after the tool response has been sent.
  - Safe default for streaming: tool turns use `prompt()`, and only the final answer streams, from a clone of the tool-free base session (the pre-warmed session below). `clone()` keeps the source session's context (01), and tools are `create()` options, so a clone of a tool session is still a tool session **[inferred]**; hence the clone of the tool-free session.
  - Cost of that default: the answer clone has none of the tool calls or results, so the tool results from the tool session are appended to it as text, as in the fallback loop (3.3 step 3). The results then sit in the context twice, once in the tool session and once in the answer clone; in a 7-9K window that second copy limits how much tool output a question can use **[inferred]**. S7 measures that cost against streaming on the tool session itself.
- Quota names in current builds: `contextWindow`, `contextUsage`, `measureContextUsage()`, `contextoverflow` event.
- First `create()` in a browser session can take 3-21 s; later ones take milliseconds. Pre-warm a base session when the panel opens and `clone()` it per question **[measured timing, 00; `clone` pattern is what DevTools Console Insights does, 01]**.
- The model must be present before `create()` from a page without user activation. The download needs a user gesture **[documented, 01; a click was sufficient, measured, 00]**.

| 1 (third-party) | Internals of third-party packages that are on the page in dev mode but not exported from their public entry points: the `@ngrx/signals` `STATE_SOURCE` symbol (its `index.ts` exports `getState`, `patchState` and `watchState`, not `STATE_SOURCE` **[measured, `modules/signals/src/index.ts` in the local ngrx clone]**), the globals that Storybook's and Vitest's own modules set (`__STORYBOOK_PREVIEW__`, `__vitest_browser_runner__`, 6.2 and 6.3), and tokens such as Analog's `DEBUG_ROUTES` or RxAngular's `RxStrategyProvider` found by token name in provider records | yes, when the package is present, but version-fragile, with no support statement from the package |
| 2 (stretch; WebMCP tools are called "app opt-in" in the rest of this document) | Needs the app to change: re-export internals to `globalThis`, add a provider, register WebMCP tools, or install a third-party devtools provider | no |

Lars's brief says: "Using internal APIs like the theta-prefixed symbols exported by `@angular/*` packages should be avoided but if features require these APIs, then exporting them to `globalThis` may be a stretch prerequisite."

Tier 1 is "using internal APIs". The difference from the case the brief names is that Angular itself already publishes these functions on `window.ng` for Angular DevTools, so they need no app change and no `globalThis` export. Lars ruled on it on 2026-10-12 (Decision 1 in section 8): Tier 1 is allowed, each use is labelled, and every Tier 1 call is feature-detected with `typeof ng[name] === 'function'`, as Angular DevTools does (`ng-debug-api.ts:24-30`). Tier 1 splits into two groups by what Angular says about them (`packages/core/src/render3/util/global_utils.ts` on the 22.2.x branch) **[measured]**:
- **Covered by a support statement:** the nine `ɵ` functions in `ExternalCoreGlobalUtils` (lines 105-136): `ɵgetDependenciesFromInjectable`, `ɵgetInjectorProviders`, `ɵgetInjectorResolutionPath`, `ɵgetInjectorMetadata`, `ɵsetProfiler`, `ɵgetSignalGraph`, `ɵgetControlFlowBlocks`, `ɵgetTransferState`, `ɵgetComponentInstanceDeepLinkId`. The comment above that interface (lines 99-104) says any function that has ever been in it exists in long-lived public versions that DevTools must support. So these nine are more stable than ordinary `ɵ` exports **[inferred from that comment]**.
- **No support statement:** `toggleWatchSignal` is in `InternalCoreGlobalUtils` (lines 78-97), a "beta" channel that Angular says it can change "more or less as much as we want"; the router trio is in `NonCoreGlobalUtils` (lines 72-76), with no statement; `__ngDebugHydrationInfo__`, the `ngDevMode` counters, `constructor.ɵcmp.debugInfo` and the `devtoolstooldiscovery` tools are in none of these interfaces. Third-party Tier 1 has no statement either.

Decision 1 in section 8 lists what drops to Tier 2 if Lars rules Tier 1 out, and which of those features rest on the group with no support statement.

Two Tier 1 rules from source:

- Never call `ng.ɵsetProfiler(null)`. It clears every profiler, including Angular DevTools' **[measured, `render3/profiler.ts:40-42`]**. Only add callbacks and keep the remover.
- A lookup with an imported class (`injector.get(Router)`) is impossible from an extension, because the extension's classes are not the app's. A lookup with a token object taken from a provider record works: the ledger's reproduction takes `ViewContainerRef` from `ɵgetInjectorProviders` and calls `inj.get` with it (`filing-ledger.md` section 1). The limit is construction, not access: `get` can create a service that was not created yet (3.2, 3.4). So prefer the `ng` helpers that do the lookup inside the app bundle (`ɵgetRouterInstance`), instances the page already holds, or duck typing, and call `get` with a record's token only under the rule in section 6 **[inferred, 02 section 1.3; 04 section 0; the record-token `get` measured, `filing-ledger.md` section 1, 05 S2]**.

Where accessibility roles and names come from (N6, N10's a11y rule, N23, and the locator suggestions in 6.3). Page JavaScript has no standard API that returns the accessibility tree **[inferred; not checked in `research/`]**. 08 names two sources:
- Computed in the page agent from the DOM: explicit `role` and `aria-*` attributes, the implicit role of the element (for example `button`, `a[href]`, `input[type=checkbox]`), and a name from `aria-labelledby`, `aria-label`, an associated `<label>` or the text content. This is Tier 0. It is a subset of what the browser computes and can differ from it in complex cases **[inferred]**.
- The CDP `Accessibility` domain through the `debugger` permission: the full tree as the browser computes it. The `debugger` permission is the reason N21 is left out of the Tier 0-only release (Decision 1), so the same rule applies here: the full tree is not part of any Tier 0 feature.

Why the `debugger` permission is left out of the Tier 0-only release: this is Claude's choice, not a constraint. Tiers are defined by data source, and Angular DevTools itself requests `debugger` as a required permission, for signal breakpoints (`manifest.chrome.json`, `breakpoint_manager.ts`; 02 sections 2.2 and 2.3) **[measured]**. The reason for the choice: `debugger` lets the extension attach the Chrome DevTools Protocol to any tab it can access, which is far more than the page reads the release needs, and Chrome shows a notice on the browser while an extension's debugger is attached **[inferred; the notice is not checked in `research/`]**. A later release can add N21 and the full tree behind `debugger` as an optional permission, requested when the user first uses them **[inferred design; optional `debugger` not checked]**.

N6, N10 and N23 use the DOM-computed roles and names and say so in their output.

- The selected element `$0` is reachable only through `chrome.devtools.inspectedWindow.eval` and `chrome.devtools.panels.elements.onSelectionChanged`, so the DevTools panel uses that second channel for the "Inspect element" row in section 5 and for "Ask about this", the way Pangular does (03 section 1.2) **[inferred; Pangular's use measured, 03]**.
- The page agent must run in the MAIN world: `window.ng` and the `respondWith` expando on the discovery event are invisible to an isolated content script **[inferred from 02 section 1.5; Angular DevTools does the same, `manifest.chrome.json`]**.
- Where the model session lives: spike S1 (`research/11`) **[measured in Chrome Beta 156 and Edge Dev 157]**.
  - Phase 1: `LanguageModel` and `LanguageModelToolCall` exist in all eight extension contexts.
  - Phase 2, on the Gemma 4 and Aion instances: seven of the eight contexts complete `create()` plus a tool round trip in both browsers. They are the DevTools panel, side panel, service worker, offscreen document, both content-script worlds and an extension tab.
  - The exception is the hidden `devtools_page`. Its `language-model` permissions policy is denied, `availability()` reads `unavailable`, and `create()` throws `NotAllowedError`.
  - So the session lives in the DevTools panel or side panel page, never the `devtools_page`.
- Recommended UI: a DevTools panel ("Angular AI") for the full chat, plus "Ask about this" entries in the Elements sidebar that open the chat with the selected element as context, following Chrome DevTools AI assistance **[documented, 03 section 3]**.

### 3.2 One tool registry, four sources

Every capability is a tool with `{name, description, inputSchema, execute}`. The Prompt API shares `{name, description, inputSchema}`: its declarations have no `execute`, because a per-tool `execute` (closed loop) is not yet in the specification or in browsers **[documented, 01: the explainer calls it "a planned future extension"]**. The registry keeps `execute` for the page agent, which runs each tool call. Angular's `ToolDefinition` (`primitives/devtools/src/tool_definitions.ts`), WebMCP and the chrome-devtools-mcp third-party tools API use the same name, description and schema, so one registry serves all four sources in the table below. App WebMCP tools keep the names the app chose, so they do not go to every model session: N9 says which sessions get them **[inferred design]**.

| Source | Tools | Tier |
|---|---|---|
| Angular's own tools via `devtoolstooldiscovery` | `angular:di_graph` (no input), `angular:signal_graph` (`{target: HTMLElement}`) | 1 |
| Extension tools over `ng.*` | section 3.4 | 0 and 1 |
| App WebMCP tools via `document.modelContext` | whatever the app registers with `provideExperimentalWebMcpTools` or Signal Forms `experimentalWebMcpTool` | app opt-in |
| Ecosystem adapters | NgRx, Storybook, Vitest, Analog, RxAngular (section 6) | 0 to 2 |

The extension also answers `devtoolstooldiscovery` with its own tool group, so when chrome-devtools-mcp (with `--categoryExperimentalThirdParty`) drives a browser in which the extension is installed (an attached browser, or the extension loaded into chrome-devtools-mcp's own profile), its users get the published subset of the Angular runtime read tools (3.5) in Claude Code or any MCP client, with no tool code beyond the one registry **[documented, 03 section 3.3]**. That the extension's group and Angular's group can both be published is **[inferred]** and unchecked: Angular's listener calls `event.respondWith(...)` once (`registration.ts`), and whether a dispatcher keeps every call or only the last is the dispatcher's choice. The only dispatchers in the evidence keep the last call (the ledger's reproduction, `filing-ledger.md` section 1), and 03 section 3.3 does not say whether chrome-devtools-mcp collects several groups. Spike S8 checks it. When the extension dispatches the event itself to collect Angular's tools (table above), its handler must keep every `respondWith` call and drop its own group **[inferred design]**.

Angular's two tools need care **[measured, 05 S2]**:

- **Never run `angular:di_graph`.** It changes the page and its output is too large. DI facts come from `ɵgetInjectorProviders`, `ɵgetInjectorResolutionPath` and `ɵgetInjectorMetadata`, which read records without instantiating anything (05 S2). `ɵgetDependenciesFromInjectable` is not a pure read either, so 3.4 limits which tokens `di_lookup` may pass to it. The evidence:
  - On a one-component 22.2 app the tool's output is 42,788 characters.
  - It calls `injector.get(ViewContainerRef)` on component hosts. After that, `ng.ɵgetSignalGraph` (and `angular:signal_graph`) lose the template node and the signals that only the template reads (`title`, `double`, `items`), for the rest of the page's life. `count` stays, because the effect also reads it (05 measured `effect, signal:count` afterwards). A draft upstream report is in `filing-ledger.md`.
  - `ɵgetDependenciesFromInjectable`'s first statement is `injector.get(token, null, {self: true, optional: true})`, and it throws "Unable to determine instance of ..." when that returns null (`packages/core/src/render3/util/injector_discovery_utils.ts:61-63` on the 22.2.x branch) **[measured in source]**. That is the call shape that breaks the signal graph for `ViewContainerRef` (05 S2).
  - On an environment injector, the same `get` constructs a provided service that was not created yet and runs its constructor **[inferred from `R3Injector.get` (`r3_injector.ts:323`, record creation at 352-358) and `hydrate` (`:529-537`); not run]**.
  - After that first `get`, the function also calls `get` for each of the class's dependencies along the resolution path (`{self: true, optional: true}` on each injector until one returns a value, and for a `host` dependency a second `get` on the first injector with the dependency's own flags instead of `self: true`; `injector_discovery_utils.ts:85-125`) **[measured in source]**. Each dependency was resolved when the instance was built, so for a class that is known to be constructed these calls return existing instances **[inferred]**.
  - Pangular avoids the same trap: its injector view "skips uncreated services to avoid instantiating them" (03 section 1.3, Injectors row) **[documented, Pangular docs at `76c09d0`, 03]**.
- `angular:signal_graph` takes `{target: HTMLElement}`, which a model cannot produce, and its description alone is 1,390 characters. The registry wraps it behind a component id from `find_components` and a short description, or calls `ng.ɵgetSignalGraph` directly. N2's write rules always call `ng.ɵgetSignalGraph` directly, because `angular:signal_graph` strips `debuggableFn` (02 section 1.5).
- `angular:di_graph`'s definition has an empty `properties` schema and a namespaced name (`angular:di_graph`), and neither is known to be safe on Gemma 4 (see 2.1). So even its definition is not passed through unchanged. (Updated 2026-10-12, S11: an empty schema passed on Gemma 4 GPU, and the name has no uppercase letter, so it meets the naming rule; a name with a colon was not tested **[measured for the schema, n=1; the colon untested]**.)

The extension's own tool group, answered through `devtoolstooldiscovery` for chrome-devtools-mcp users, follows the same rules and holds only MAIN-world read tools (3.5). Whether it is published next to Angular's group is unchecked (above, S8).

### 3.3 The model loop

Before any of the steps below, the panel runs `app_facts` once per page load. If its zone-mode check reads Zone.js change detection (3.4), the panel shows a "not supported: this panel supports zoneless apps only" notice, creates no model session, and runs no other tool **[inferred design]**. A zoneless app that loads zone.js passes the check.

1. **Intent and tool subset.** A fresh clone of a warm session gets the question and a list of tool groups, and returns `{groups: [...]}` under `responseConstraint`. Only those groups' tools go into the next session. Small models choose worse among many tools, and every tool schema costs context **[inferred; tool count per session is a spike, S3]**.
2. **Tool session.** `create({tools, expectedInputs, expectedOutputs, initialPrompts: [system, context chip]})`. The context chip is a short line naming what the user has selected (a component or element) and the app facts from N18, shown in the panel and sent as context. The chip shows nothing about zone mode: every app that reaches the chat passed the zoneless support check above **[inferred design]**. Loop: `prompt` -> run each `tool-call` in the page agent -> send `tool-response` -> repeat, with a step cap (Chrome's own assistant caps at 20 **[measured in DevTools source, 01]**; start at 6 for a 7K window **[inferred]**).
3. **Structured-output loop.** Used where `tools` is missing or ignored (Chrome 154 stable with the flag off), and wherever the routing rule below chooses it. The same loop runs on structured output.
   - The model returns `{"tool": name, "args": {...}}` or `{"answer": "..."}` under a `responseConstraint` built from the tool schemas.
   - Tool results are appended as text.
   - Neither the API nor `create()` tells whether tools work. Chrome 154 accepted `tools` silently and never called them **[measured, 00]**.
   - Chrome Beta defines `LanguageModelToolCall` and `LanguageModelToolSuccess` and accepts a tool session. Yet its tool prompts failed with `kErrorUnknown` in 00's probes **[measured, 00]**, the same symptom that S1 phase 2 measured as a model-process crash (11) **[inferred for 00]**. 00 blamed tools with no parameters. That cause is confounded, and the camelCase tool name alone reproduces the crash (see the quirks in 2.1) **[measured, 11]**. S11 then showed that an uppercase letter in the name is the trigger and that an empty schema works on Gemma 4 GPU (2.1) **[measured, n=1 per variant]**.
   - So run the startup check (both canaries on Edge, the structured-output canary alone on Chrome) when the panel opens and no cached result matches the key (below) **[inferred design]**:
     - Native canary: one round trip with a `ping` tool and "Call ping.". The canary follows the naming rule of every other tool (3.4, 3.6): `ping {scope: {enum: ['page']}}`, lowercase. It keeps one required parameter although the rule no longer asks for one (2.1), because that is the shape of the S11 control that passed on Gemma 4 GPU, and a canary that also returns an argument checks the `arguments` getter that every later tool call depends on **[inferred design]**. It passes if a `tool-call` part comes back and the follow-up prompt succeeds. A pass does not by itself choose native tools; the routing rule below does.
     - The native canary runs only on Edge. On Chrome the routing rule sends the model to the structured-output loop whatever the native canary says, so its result cannot change the route there, and a `kErrorUnknown` from it could add a crash toward Chrome's three-crash limit (2.1). A native tool session on Chrome comes only from the manual override, which does not consult the canary **[inferred design]**.
     - Structured-output canary: a one-step prompt under a small `responseConstraint`. If the reply is empty or is not valid JSON, the fallback loop cannot run on the model, so the routing rule below marks it unsupported unless it goes to native tools. Nano on the CPU backend is the measured case: its fallback failed 15 of 15 runs, 14 with empty or cut-off JSON (2.1). The extension cannot read the backend (2.1), so this check is how it finds out. One of those 15 runs returned valid JSON, so a single passing reply is not enough: repeat the canary three times and require all three **[inferred from the 14 of 15 rate]**.
     - The check runs without blocking the chat and stops at the first failure (one failure already marks the model unsupported). A question asked before the check finishes uses the cached result when one matches the key; with no cached result it runs on the structured-output loop, the route of every supported model except Aion, which also passed 11/15 on it (2.1). If the check then marks the model unsupported, that answer is stopped and replaced by the unsupported message. When the manual override is set, it decides, as always **[inferred design]**. A passing result runs once per cache key (below); an unsupported result is checked again (below) **[inferred design]**. The reason is its cost on Nano CPU:
       - In `research/raw/bench/nano.json` the fallback questions have medians of 34-42 s per question **[measured]**.
       - 14 of the 15 failed runs threw on the JSON parse (`SyntaxError: Unexpected end of JSON input`), and the harness saves such runs with `calls: []` from its catch block, so their calls are not recorded (`bench.js:168`); the 15th answered in text with no tool call **[measured]**. So that each failed run was a single prompt is **[inferred]**.
       - Three repeats could hold the panel for about two minutes at first open (three repeats at 34-42 s are 102-126 s); the canary's schema is smaller than the benchmark's, so that is an upper bound **[inferred]**.
     - The fallback's `responseConstraint` part is measured to work on Gemma 4 (GPU and CPU), Aion, Phi-4-mini and Nano on GPU, and to fail on Nano on CPU **[measured, 05]**.
   - Cache the canary results (two on Edge, the structured-output result alone on Chrome) under a key of user agent and `contextWindow`, and check again in two cases: a loop reply that comes back empty or as invalid JSON runs the structured-output canary again, and a cached unsupported result is checked again at each panel open **[inferred design]**. The reasons:
     - The key notices only a major-version change or a window change. Every saved benchmark run records a reduced user agent with no build number (`Chrome/156.0.0.0` on Chrome Beta, `Chrome/157.0.0.0 Edg/157.0.0.0` on Edge Dev, `Chrome/155.0.0.0 Edg/155.0.0.0` on Edge stable; `ua` field of `research/raw/bench/*.json`) **[measured]**, and the key cannot tell Nano from Gemma 4 or a GPU backend from a CPU backend.
     - Keying on the browser version, or on the user agent, is not enough on its own: the Nano and Gemma 4 instances are both Chrome Beta 156.0.8078.17 with `contextWindow` 9,216 (00, 05), and Nano's backend follows the stored performance class, which Chrome measures at startup (00, "Choosing CPU or GPU per instance"), so the same version can move Nano from GPU (fallback 11/15) to CPU (0/15). That the class changes between startups on one machine is **[inferred]**, not observed.
     - An empty or invalid JSON reply is the measured Nano CPU symptom, so running the canary again on it catches the move from GPU to CPU.
     - The reverse move, from CPU back to GPU, produces no loop reply to react to, because an unsupported model runs no loop. So while unsupported is the cached result, each panel open runs the structured-output canary once more in the background (it stops at the first failure), the "unsupported" message has a "Check again" control, and the message points to the manual override (routing rule below) **[inferred design]**.
   - **Routing rule [inferred from measured per-model results]**, applied in this order; the first bullet that applies decides:
     - Native tools when the browser is Edge, `contextWindow` is 7,168 (Aion as measured; Phi-4-mini on Edge stable reports 9,216) and the native canary passes. The structured-output canary does not decide this case.
     - Otherwise, the structured-output loop, if the structured-output canary passes three times out of three.
     - Otherwise (the structured-output canary failed), the model is unsupported (Nano on the CPU backend).
     - No API in the evidence names the model: 2.1 lists what the browsers do not tell, and the model names in 00 come from manifests and `on-device-internals`, which the extension cannot read. So the rule is a heuristic. An Edge update can change the window or the model and break the 7,168 test. The panel settings give the user a manual override: native tools, structured-output loop, or automatic. Spike S13 looks for an in-API signal that tells the models apart.
   - **After a `kErrorUnknown` on Chrome, do not retry automatically [inferred design].** The extension stops the question, shows the error, tells the user that Chrome may count it toward its three-crash limit (2.1), and prompts again only when the user retries. It also keeps its own count of these errors and shows it with the error. The count resets on any successful prompt, as Chrome's count does (2.1). It is a lower bound: the extension cannot see crashes caused by other pages or extensions. The reasons:
     - Chrome disables the on-device model for the whole browser after three crashes with no successful response between them, and a retry loop could reach that limit by itself (2.1).
     - Snake_case names with a required parameter do not prevent the error: the Gemma 4 benchmark run in 2.1 followed that rule and still failed **[measured, `research/raw/bench/gemma4.json`]**.
     - 3.6's "retry once on a tool error" covers a tool that returns an error, not a failed session, so it does not apply here.

   Why `availability()` cannot decide this:
   - In Chrome 156 the tool types are gated by the Blink runtime feature `AIPromptAPIToolUse`, not by the model. With the feature off, `create()` refuses any `tool-call`/`tool-response` type with "unable to create a session". `availability()` still says `available`, because it never checks tool types, which contradicts the spec **[measured: probe matrix 05, Chromium 156.0.8078.17 source 09]**.
   - With the feature on, Gemini Nano opens tool sessions but answered with text instead of a tool call in all three tries **[measured, 05]**. In the benchmark, none of Nano's 15 native GPU runs made a tool call. Nano's native passes (2/15 GPU, 1/15 CPU) made no tool call **[measured, `research/raw/bench/nano-gpu.json`, `nano.json`]**, so they are grader artifacts: two are code-text answers to question 1 that passed its number check (where the "2" sat is **[inferred]**, because saved answers are cut at 160 characters), and one is an untooled guess (2.1). No Google source claims tool calling for Nano **[measured by search and page reads, 10]**.
   - So the routing rule above gives, as in 2.1: Aion, native tools; Gemma 4, Gemini Nano and Phi-4-mini, the structured-output loop; Nano on the CPU backend, unsupported. Native tools on Gemma 4 only after S4 improves tool choice and argument accuracy and S13 finds a way to tell Gemma 4 from Nano.
   - Microsoft documents Aion 1.0 Instruct as a text model; no source describes Aion-1.1-Instruct, the version Edge Dev 157 serves. Its tool calls come from Edge's runtime workaround (`msEdgeLLMOnDeviceModelMuffinToolUseWorkaround`), so they can change with an Edge update **[documented, 10; the link between the workaround and Aion measured, 00: the flag's description in Edge Dev 157 names "the on-device Aion model family"]**.
4. **Answer rendering.** Answers show the tool walkthrough (each call, its arguments, a short result, a Reveal link to the element, the component in the tree, or the source), as Chrome DevTools AI assistance does **[documented, 03 section 3.1]**. The walkthrough is what makes a small model's answer checkable.
5. **Context budget.** `contextoverflow` fires after the API has already evicted the oldest prompt and response pairs **[documented, 01 section 1]**, and that eviction removes the user's question before old tool results (07 section 4). So the trigger for summarizing is a budget check before the window fills: before each `prompt()`, call `measureContextUsage()`, and if the result would leave less than about 1,000 tokens free, summarize the conversation with the Summarizer API (available in both browsers **[measured, 00]**) into a new session's initial prompts **[inferred, 07 section 4]**. `contextoverflow` is only a fallback: on it, rebuild the session from the panel's own transcript **[inferred design]**.

### 3.4 Core tool set

Designed after Pangular's agent tools and React DevTools' lazy detail protocol **[documented: Pangular docs at `76c09d0` and React DevTools, 03 sections 1.5 and 2.2]**: a small tree with ids, details on demand, hard output caps with "N more, narrow with X" messages, and stable ids from a `WeakMap`.

**Tools take ids, not selectors.** `find_components` returns short ids (`c3`), and every tool that targets a component takes `{id}`. The evidence **[measured, counted from `research/raw/bench/*.json`; table and counting rule in 2.1]**:
- Bad arguments (an invented CSS selector, a signal name in the selector field, or a wrong signal name) caused 3 of Aion's 4 fallback failures, 3 of Phi-4-mini's 8 fallback failures, 2 of Gemma 4 GPU's 2 fallback failures, 3 of Nano GPU's 4 fallback failures, 2 of Gemma 4 GPU's 7 native failures and 3 of Gemma 4 CPU's 6 native failures (2 of them invalid selectors that made the harness throw). Ids remove the selector part of that class.
- Signal names are checked against `list_signals` (below), but that check catches only names that do not exist. A real but wrong signal (`count` for a question about `double`, 2 of Nano GPU's 4 fallback failures) passes it. That is a question-understanding error, which ids and lists do not address.
- A second class, choosing the wrong tool or stopping after one call without an answer, caused 4 of those 7 Gemma 4 GPU failures, the other 3 of Gemma 4 CPU's 6 native failures and 3 of Phi-4-mini's 8 fallback failures. Ids do not address it; S4 does.

The names in the table are the names the model receives. Every argument that names something takes a value that a list tool returned or an `enum`, and every tool checks its arguments itself, on every model **[inferred design]**. The details:
- The names follow the rules in 3.6: lowercase names (snake_case recommended for readability), no optional parameters, and no free-text arguments. A tool with nothing to ask may take an empty `properties` schema; the earlier rule of at least one required parameter (`scope: {enum: ['page']}`) was relaxed after S11 (2.1). `set_writable_field.value` is the one argument whose content the model writes; the tool checks it against the field's current type (table) **[inferred design]**.
- Where each value comes from: `id` from `find_components`; `signal` is a signal label from `list_signals`; `token` is a token name from `di_path`'s list or from the error message that N4 captured (a `NullInjectorError` names the missing token, which is on no provider record and so never in `di_path`'s list); `field` is the name of a writable signal field or a plain field, both from `inspect_component`. `inspect_component` finds writable signal fields with Tier 0 calls: a field whose value passes `ng.isSignal` and has a `set` method, which is the test Angular's own `isWritableSignal` makes (`packages/core/src/render3/reactivity/api.ts:55-57`) and Angular DevTools applies before a write (`property-mutation.ts:93-99`) **[measured in source; its use here inferred design]**. So `set_writable_field` does not depend on `list_signals` (Tier 1) and stays in the Tier 0-only release.
- Tools are fixed at `create()` (07 section 2), so where the set of values is known when the session is created (component names, rule ids), the argument is an `enum`. Where it is not (the signal labels of a component found later), the argument is a string that the tool checks against the list tool's output, and a miss returns the error template with up to 10 valid values (3.6). Aion probably does not enforce `enum`s (inferred in 3.6), so that check runs on every model **[inferred design]**.
- `di_lookup` checks `token` against both sources: a name in neither `di_path`'s list nor a captured error message returns the error template; a name from an error message that is on no provider record along the path returns the no-record answer (next paragraph), not an argument error **[inferred design]**.

**`di_lookup` answers from provider records, not from `injector.get`** **[inferred design]**:
- It walks the `ɵgetInjectorResolutionPath` path and reads `ɵgetInjectorProviders` on each injector; the first injector whose records hold the token is where it resolves, unless injection flags or view-provider visibility say otherwise (next bullet).
- Limits of that walk: it ignores injection flags (`@Self`, `@SkipSelf`, `@Host`, `@Optional`), which change where a dependency resolves, and it does not apply `viewProviders` visibility. A record marked `isViewProvider` (02 section 1.2) is visible only inside its component's own view, not to content projected into it (06, `hierarchical-injectors.md`), so for a projected child the walk can name a parent's view provider as the source. So the walk skips `isViewProvider` records on an injector whose view does not contain the asking node, the answer is worded "resolves here unless injection flags say otherwise", and for the classes on the host, `ɵgetDependenciesFromInjectable`'s answer (which reads each dependency's own flags, 3.2) is used instead of the walk **[inferred design]**.
- When no record on the path matches, it answers "no provider record on this path; a `providedIn: 'root'` token gets a record only when it is first injected", never a flat "not provided".
- It calls `ɵgetDependenciesFromInjectable` only with `instance.constructor` of a component or directive on the host, never for a service token or a node-injector special token.
- `di_path` drops the six special tokens from the token names it gives the model.

The evidence:
- Neither `ɵgetInjectorResolutionPath` nor `ɵgetInjectorProviders` instantiates anything (3.2).
- A missing record does not prove that the token is not provided: an `R3Injector` creates the record for a `providedIn` token, and emits the provider-configured event that `ɵgetInjectorProviders` reads, only the first time something calls `get` for that token (`packages/core/src/di/r3_injector.ts:352-358` on 22.2.x) **[measured in source]**. So a `providedIn: 'root'` service or token that nothing has injected yet is on no record. 6.4 and spike S12 describe the same case for Analog's `DEBUG_ROUTES`.
- `ɵgetDependenciesFromInjectable` calls `injector.get` for the class and for each of its dependencies along the path (3.2), so it is safe only on a token that is known to be constructed on that injector. The only such tokens are the component and directive classes on the host, which the tool gets as `instance.constructor` of an instance from `ng.getComponent` or `ng.getDirectives` on that element. Angular DevTools calls it the same way (`instance.constructor`, `devtools/projects/ng-devtools-backend/src/lib/directive-forest/component-tree/component-tree.ts:155-158, 340`) **[measured in source]**.
- No `ɵ` function reports whether a service on an environment injector has been constructed (`ProviderRecord` has `token`, `isViewProvider`, `provider` and `importPath` only, `render3/debug/injector_profiler.ts:129-149`) **[measured in source]**, hence no service tokens.

**`app_facts` reads the change-detection mode from provider records, not from a feature mark or `typeof Zone`, and uses it only as the support check (3.3).** It walks `ɵgetInjectorResolutionPath` from the node injector of the `[ng-version]` root element to the first environment injector whose `ɵgetInjectorProviders` records hold `NgZone`, matched by token name as in 2.2. **The last `NgZone` record in that injector's list decides:** `useClass: NoopNgZone` means zoneless (supported), and anything else (in the measured case a `useFactory` record) means Zone.js (not supported). `typeof Zone` says only whether zone.js is loaded. The walk catches the error that `ɵgetInjectorProviders` throws on the null injector at the end of the path **[inferred design]**. The evidence:
- Why the last record: a Zone.js app has two `NgZone` records on the same injector. Both bootstrap paths put `provideZonelessChangeDetectionInternal()` before the app's own providers (`application/create_application.ts:67-71`, `platform/platform_ref.ts:51-56`), so its `NoopNgZone` record comes first and the `useFactory` record from `provideZoneChangeDetection()` comes after it (`ng_zone_scheduling.ts:94-95`). `R3Injector.processProvider` emits a provider-configured event for every provider, and `records.set` keeps only the last record per token (`di/r3_injector.ts:521`), which is why the app runs with Zone.js. The profiler appends every event to the injector's list with no de-duplication (`render3/debug/framework_injector_profiler.ts:320-324`), so `ɵgetInjectorProviders` returns both records **[measured in source]**. A rule that reads the first `NgZone` record, or any `NoopNgZone` record, reports every Zone.js app as zoneless and lets it past the support check.
- Do not use the `provideZoneChangeDetection token` record (`PROVIDED_NG_ZONE`, `ng_zone_scheduling.ts:166`) as the test: `@angular/upgrade` provides the zone through `internalProvideZoneChangeDetection({})` directly (`packages/upgrade/static/src/upgrade_module.ts:149`, `downgrade_module.ts:386,392`), which adds the `NgZone` `useFactory` record but no `PROVIDED_NG_ZONE` record, so a hybrid app, which is also an NgModule app, would read as zoneless and pass the check **[measured in source]**.
- `performanceMarkFeature('NgZoneless')` is called only inside the public `provideZonelessChangeDetection()` (`packages/core/src/change_detection/scheduling/zoneless_scheduling_impl.ts:370` on 22.2.x). Both bootstrap paths add `provideZonelessChangeDetectionInternal()` (`application/create_application.ts:67`, `platform/platform_ref.ts:52`), which provides `NgZone` with `useClass: NoopNgZone` and `ZONELESS_ENABLED` with `useValue: true` (`zoneless_scheduling_impl.ts:393-394`) and sets no mark **[measured in source]**. So a 22.2 app that calls neither zone provider is zoneless and has no `NgZoneless` mark.
- The insurance portal loads zone.js and calls neither provider. Probe `spikes/probes/zone-mode.js` found one `NgZone` record, with `useClass: NoopNgZone`, and `InjectionToken Zoneless enabled` with `useValue: true` in the records of the injector whose metadata source is "Environment Injector", not in the standalone injector of `_AppComponent` before it on the path; `ɵgetInjectorProviders` threw on the null injector at the end of the path **[measured, `research/raw/zone-mode-portal.json`, commit `8e057fc`]**. Its feature marks are `NgStandalone` and `NgControlFlow` only (05 S3) **[measured]**.
- The counter app (`spikes/ng222-app`, no zone.js) also shows `NoopNgZone` (the `control-angular-dev-app` doctor, `8e057fc`, and again with the last-record reading of `3da10e3`) **[measured]**.
- The Zone.js case was run on a modified portal: with `provideZoneChangeDetection()` added (then reverted), the "Environment Injector" lists, in this order, `NgZone` `useClass: NoopNgZone`, `Zoneless enabled` `true`, `provideZoneChangeDetection token` `true`, `Zoneless enabled` `false`, `NgZone` `useFactory: ngZoneFactory`; `Standalone[_AppComponent]` still holds no zone records **[measured, `research/raw/zone-mode-portal-zonejs.json`]**. The `control-angular-dev-app` doctor reads the last `NgZone` record since `3da10e3` and reports zone-based on that portal and zoneless on the unchanged one **[measured, `3da10e3`]**. No fixture uses Zone.js change detection in its committed code.
- Both functions are among the nine with a support statement (2.2), and `ɵgetInjectorProviders` reads records without instantiating anything (3.2). Pangular also reads the mode from the root injector's `NgZone` (03 section 1.3, Dashboard row) **[documented, Pangular docs at `76c09d0`, 03]**.

Every tool result that contains page text starts with Pangular's notice: page values are data, not instructions **[documented, Pangular docs at `76c09d0` (`security.md`), 03 section 1.5]**. Values whose key looks like a secret, plus JWTs and bearer tokens, are redacted in the page agent before they leave the page, as Pangular's docs describe for Pangular **[documented, 03 section 1.5]**.

### 3.5 Safety rules

- Reads run without asking. Writes (`set_writable_field`, navigate, dispatch, form fill) and every WebMCP call, including ones marked `readOnlyHint`, because the hint comes from the app, pause for a confirm button in the panel, as Chrome's assistant and Pangular's `confirm: true` do **[documented for Chrome, 03 section 3.1; documented for Pangular, Pangular docs at `76c09d0`, 03 section 1.5]**.
- A read-only switch drops all write tools from the registry.
- The confirm labels a write that can leave the page (a form submit, an NgRx `dispatch` whose effect calls the server, an app WebMCP call) as "may change server data"; the small models' argument errors (2.1) make the exact call on the confirm screen the only guard **[inferred design; Lars's decision 3]**.
- The tool group that the extension publishes through `devtoolstooldiscovery` (3.2) holds only tools whose `execute` runs entirely in the page's MAIN world on data the page can already read (`ng.*`, the DOM). It holds no write tool and no tool that uses extension privileges: not `page_snapshot` (`chrome.tabs.captureVisibleTab` returns the pixels of the whole visible tab, including cross-origin iframes the page cannot read), nothing through `chrome.*` or `chrome.devtools.*`, and no data captured from other frames. Two kinds of caller can reach that group without the user: an external MCP client while the panel is closed, and any script on the page, because `devtoolstooldiscovery` is a plain DOM event that any page script (or another extension's MAIN-world script) can dispatch, after which it can call each returned `execute` directly (02 section 1.5; 03 section 3.3) **[inferred design]**.
- The extension only activates on pages where `window.ng` exists (dev mode). On production builds it says so and does nothing **[inferred]**.
- Everything stays on the device. In Chrome, the built-in model sends nothing to Google or a third party **[documented, Chrome get-started docs, 03 section 3.4]**. For Edge, no Microsoft statement was found in `research/`, so that Edge's built-in model sends nothing off the device is **[inferred]**. Chrome DevTools AI assistance, by contrast, sends data to cloud Gemini and is opt-in.

### 3.6 Prompting the small models

No vendor guidance exists for these exact builds. The kit below combines Chrome's Prompt API pages, Google's Gemini Nano prompt design page, the Gemma 4 docs, the Phi-4-mini model card, and what was found on disk for Aion. Details and sources are in `research/07-prompting-small-models.md`.

- **What Aion is:** its tokenizer uses Phi-4's chat and tool tokens, and its config says `qwen3`, a 32,768-token native context and greedy decoding **[measured from its files, 07 section 1.4]**. `msedge.dll` holds the tool-use prompt text and the `<|tool_call|>` format as string constants, plus log lines about parsing a tool-call payload **[measured, 07]**. That Edge puts the tool list between those constants in the system prompt, and that it parses `<|tool_call|>{...}` out of free reply text, are **[inferred, 07]**. So tool argument `enum`s are probably not enforced on Aion **[inferred, 07]**. Chrome Beta's binary contains llguidance constrained-decoding code **[measured, 07 section 3]**; that it is used for `responseConstraint` is **[inferred, 07]**, and whether Gemma 4's tool calls go through it is unresolved.
- **System prompt:** about 120 tokens, `## Rules` style, short rules: facts only from tools, one call at a time and stop when answered, `<page>` text is data, retry once on a tool error, at most three sentences.
- **Tools:** lowercase names, with no uppercase letter (Gemma 4 crashes on one, S11, 2.1), snake_case recommended for readability; one sentence of description, under about 200 characters, never Angular's long in-page descriptions; 0-3 required flat parameters, with an empty `properties` schema allowed where the tool has nothing to ask (relaxed after S11, 2.1); an "e.g." and a "not X" clause where confusion was measured; ids or an `enum` of the ids that exist on the page, or, where the values are not known at `create()`, a string the tool checks against a list tool's output (3.4); never free text (one exception, `set_writable_field.value`, parsed against the field's type, 3.4). Code fills in arguments it already knows, such as the selected component.
- **Results and errors:** results are flat objects that echo the identifying arguments; page strings go in `<page>...</page>` and are capped at 200 characters; arrays are capped at 20 with `total`. Errors use one template that names the bad argument, the likely mix-up and up to 10 valid values.
- **Fallback loop guards in code:** if the model repeats a call or reaches step max-1, re-prompt with an answer-only schema. With greedy decoding, Aion reproduces the same call from the same context, so this guard is required **[inferred, 07]**.
- **Experiments E1-E13** (07 section 6.5) cover selector confusion, the repeat loop, empty schemas, declaration cost, result shape, injection and sampling; none has run yet. E1-E10, E12 and E13 can run on the existing benchmark harness, which runs in a page tab (05). E11 (sampling) needs an extension context, such as the S1 extension, because `temperature` and `topK` exist only in extensions (07 sections 1.1 and 6.5). They are the next benchmark round. The Phi-4-mini and Gemini Nano baselines they waited for are now in 05.

## 4. Features: new capabilities (main priority)

Test for "new": the model does something a panel cannot, such as explain a cause, connect facts across views, judge against a rule, or produce an artifact. Each of N1-N13 lists an example prompt or trigger, the tools it uses, the tier, and the built-in AI APIs. The N14-N23 table lists the prompt, the data and the tier but no API: N18 is code that runs before the model, and the others explain their data through the model loop in 3.3, which uses the Prompt API with tools or with structured output by the routing rule **[inferred design]**.

### N1. "Why did this update?" change-detection causality

- Prompt: "Why did `app-cart` re-render when I typed in the search box?"
- How: `cd_record` subscribes through `ng.ɵsetProfiler`. Per cycle it records the event that started it (output listener, DOM listener via `getListeners`, signal write seen as a template consumer epoch change, `applyChanges`, timer). Per component, it records whether the template ran and which bound signals changed epoch. The model gets a per-cycle fact list and explains the chain: "the `input` listener on `app-search` set `query`, `app-cart` reads `filteredItems`, which is computed from `query`, so its template ran" **[inferred; event list measured in `packages/core/primitives/devtools/src/profiler_types.ts:22-156`]**. The event list has no timer event; the only listener event is `OutputStart`, which `listeners.ts:90` fires for template and host listeners **[measured in source, 22.2.x]**. So a timer or another trigger that is not a listener is named by elimination (a `ChangeDetectionStart` with no `OutputStart` before it) **[inferred]**. N1 does not read the zone task, even when zone.js is loaded: a zoneless app can load zone.js, as the insurance portal does (3.4, `app_facts`) **[measured, `research/raw/zone-mode-portal.json`]**, and in such an app the zone task did not start the cycle **[inferred]**.
- Adds over Angular DevTools: its profiler shows time per component and flame graphs. It does not follow the chain from a trigger through signals to each component that was checked; N1 adds that per-component chain, which a zoneless app (the 22.x default and the only supported kind) has no other record of. Note: Angular DevTools fills a frame's "Source" from `Zone.currentTask.source` whenever zone.js is loaded (`ng-devtools-backend/src/lib/profiling/capture.ts:373-379`) **[measured, Angular DevTools source on the 22.2.x branch]**; in a zoneless app that loads zone.js it likely names the zoneless scheduler's timer or microtask, not the trigger (`util/callback_scheduler.ts:54-59`, `zoneless_scheduling_impl.ts:218-223`) **[inferred from that source; not run]**. Pangular's change-detection recorder shows recent cycles with the triggering output listener **[documented, Pangular docs at `76c09d0`, 03 section 1.3]**; it does not explain them with a model. This is React DevTools' "Why did this render?" applied to Angular's signal and zoneless model **[documented, 03 section 2.1]**.
- Tier 1 (`ɵsetProfiler`, `ɵgetSignalGraph`). Prompt API with tools.

### N2. Signal provenance and reactive anti-pattern finder

- Prompts: "Where does the value of `total` come from?", "Is anything in this component an effect that should be a computed?"
- How: `signal_trace` walks producers from a node back to writable sources; the model narrates the chain with labels (labels come from compiler-inserted `debugName`, `implicit_signal_debug_name_transform.ts` **[measured, 02 section 5.3]**). A deterministic rule pass over the graph, plus a source-text scan for writes (below), flags patterns, and the model explains each finding and proposes the rewrite:
  - an `effect` whose only job is to write another signal (prefer `computed` or `linkedSignal`);
  - a cycle or an effect that writes a signal it reads (possible loop);
  - a `resource` whose params read a signal that changes per keystroke (the `design-patterns.md` advice on separate input and submitted signals, `design-patterns.md:5-39` **[measured]**);
  - unlabeled nodes (suggest a `debugName`, Solid devtools idea **[documented, 03 section 4.6; from a search summary, not a page read]**). An effect created without assignment, as in the counter app's constructor (`effect(...)` as a bare statement in `spikes/ng222-app/src/app/counter.ts`), has an empty label (05); one assigned to a variable or a field, or with `this.x = effect(...)`, gets its name from the compiler, because the transform covers those three cases for `effect` and `afterRenderEffect` (`implicit_signal_debug_name_transform.ts:127-210`, `:224-238`; 02 section 5.3) **[measured in source]**. So this rule skips effects, and findings name an effect by its label when it has one, otherwise by its owning component and its source text **[inferred design]**.
- How the write rules see writes: the signal graph alone cannot see them. `ng.ɵgetSignalGraph` has read edges only, and a signal that nothing reads is not a node. On `spikes/ng222-app` the effect that writes `lastLogged` appears only as `effect -> signal:count` **[measured, `spikes/probes/effect-writes.js`, `9959d32`, 05]**. The profiler events include no effect runs either **[measured in source, 05]**. The route that works: each effect node keeps `debuggableFn`, and its source text there is `() => this.lastLogged.set(this.count())`, in which a scan for `.<name>.set(` and `.<name>.update(` found `lastLogged.set` **[measured, same probe]**. The scan reads `ng.ɵgetSignalGraph` directly, because `angular:signal_graph` strips `debuggableFn`, and it needs Angular 22.1.3 or later, when non-computed nodes got the field (02). It is a heuristic **[inferred]**: writes made through a called method or another object, writes without `this.`, and minified code were not tested and can be missed. Findings from these two rules say so.
- Rule detection is code; the model only explains and drafts the fix. That keeps findings deterministic while the prose adapts to the code **[inferred design choice]**.
- Tier 1. Prompt API with tools and structured output (findings schema: rule, node, severity, fix).

### N3. DI doctor

- Prompts: "Why do `ProductList` and `ProductDetail` get different `CartService` instances?", "Where would `AUTH_CONFIG` resolve from here?"
- How: `di_path` plus `di_lookup` for both components, then a diff of the two resolution paths. Both read provider records along each path and construct nothing; `ɵgetDependenciesFromInjectable` runs only on the component's own class (3.4). The model explains which injector provides each instance (component `providers`, route environment injector, root) and suggests the provider change. The answer carries `di_lookup`'s limit: injection flags such as `@SkipSelf` or `@Host` on the injecting class can move the real source, and the walk does not see them (3.4) **[inferred design]**. For `NullInjectorError` caught by N4, it reconstructs the path at the failing component and passes the token name from the error message to `di_lookup`, which reports "no provider record on this path" (3.4). For "Where would `AUTH_CONFIG` resolve from here?" the same answer is worded with its caveat: a `providedIn: 'root'` token that nothing has injected yet has no record, so the model says that the token may still resolve at root once it is first injected, not that it is missing (3.4) **[inferred design]**.
- For a question about the whole app, it runs `di_path` and `di_lookup` over the relevant components. It never runs `angular:di_graph`, which section 3.2 forbids.
- Tier 0 (`getInjector`) plus Tier 1 (injector functions). Prompt API with tools.

### N4. Angular error explainer (on-device Console Insights for Angular)

- Trigger: an uncaught error or `console.error` containing `NG0` / `NG0xxxx` codes, or a click on "Explain" in the panel's error list.
- How: the page agent hooks `window.onerror`, `unhandledrejection` and `console.error`, keeps the stack and the element if the error carries one, and maps it to a component with `ng.getOwningComponent`. The model gets: error code, message, the component's inputs and listeners, and the matching entry from a bundled offline digest of `angular.dev/errors` (shipped with the extension, no network). It answers "what happened, in this component, and the likely fix."
- The digest's source: the angular repo's `adev/src/content/reference/errors` on the 22.2.x branch, 61 `NG*.md` pages (plus `overview.md` and a `BUILD.bazel`), 95,095 bytes in all, about 24K tokens at 4 characters per token; the largest page is 4,758 bytes (`NG0991.md`), about 1,200 tokens **[measured byte count; token sizes estimated]**. The repo's `LICENSE` is MIT, with Google LLC's copyright line **[measured; not legal advice]**. The whole set cannot sit in a 7-9K window, so the digest stores one entry per code, cut to at most 150 tokens when the extension is built, as `get_rule` caps a rule (N10), and only the matching entry goes to the model. The bundled text keeps the MIT notice and the copyright line, as N10's skill text does **[inferred design]**.
- Adds over Chrome Console Insights: Console Insights' full explanation runs on cloud Gemini under opt-in **[documented, 03 section 3]**; its short "teasers" already run on-device through the Prompt API (`BuiltInAi.ts`) **[measured, 01]**. N4 adds Angular error codes, the owning component and its inputs and listeners, and a full explanation on-device.
- Tier 0. Prompt API with tools; Summarizer for long stacks.

### N5. Hydration and `@defer` doctor

- Prompts: "Why is the reviews block still on its placeholder?", "Why did hydration skip `app-map`?"
- How: `defer_blocks` gives state, triggers and incremental hydration state; `hydration_status` gives per-node mismatch details (expected vs actual node). The model correlates triggers with what happened (for example an `on viewport` trigger on an element that is never visible, or a `hydrate never` block). This is React DevTools' "suspended by" applied to `@defer` **[documented, 03 section 2.3]**.
- Prior art: Pangular's component view already lists `@defer` blocks with state, triggers, hydration state and "hydrate never" **[documented, Pangular docs at `76c09d0`, 03 section 1.3]**, and its tool output goes to an external agent. New here: an on-device model correlates the triggers with what happened, and the app installs nothing.
- Tier 1. Prompt API with tools.

### N6. Capture-to-test: a Vitest Browser Mode spec from live state

- Prompt: "Write a test for this component as it is now."
- How: capture the selected component's class name, inputs (current values), DOM listeners and outputs, the roles and names of its host and children (computed from the DOM, 2.2), and optionally a short interaction recording (clicks, input events, resulting input/DOM changes). A deterministic template produces a `vitest-browser-angular` spec (`render(Component, {inputs})`, `page.getByRole(...)` queries, `expect.element(...)` assertions) **[render API measured in 04 section 4]**. The model fills only the parts that need judgment: test names, which assertions matter, which recorded steps are noise. Structured output keeps it to a schema `{tests: [{name, steps, assertions}]}`.
- Class name and import path: the class name comes from the instance's constructor, with the leading underscore of dev-build class names (`_AppComponent`) stripped, as `find_components` does (05, S3). The spec's import path needs the component's source file, and the only source of file and line in this document is `constructor.ɵcmp.debugInfo` (N13), which is Tier 1 with no support statement (2.2). In a Tier 0-only release the spec leaves the import path for the developer or the coding agent to fill in, unless a check shows that N13's `inspect()` route can return the file **[inferred design]**.
- Delivery without a repo bridge: copy, download, or a File System Access directory handle the developer picks. With the Angular CLI MCP server or a coding agent, "Copy to coding agent" hands over the spec plus the file path where one is known (above) **[inferred design; Vitest facts measured, 04 section 4]**.
- Lars's testing position applies: assertions are on the rendered DOM, not on instance fields; no jsdom. Source: Lars's `lars-frontend-dev` skill (`~/.claude/skills/lars-frontend-dev/SKILL.md`, the Testing bullet), not the evidence set.
- Tier 0, plus Tier 1 for the import path from `ɵcmp.debugInfo`. Prompt API with structured output; Writer for test names is optional.

### N7. Interaction story and bug report

- Prompt: "Turn what I just did into a bug report."
- How: a recorder in the page agent logs user events with the target component, the CD cycles they caused (N1 data), signal value changes (the per-cycle epoch changes in N1's `cd_record` data, read from `ng.ɵgetSignalGraph`, one of the nine functions with a support statement; not `toggleWatchSignal`, which only logs to the console, 02) **[inferred design]**, router navigations, console errors and network failures. The model writes "steps to reproduce, expected, actual" with component names, and the Writer API adapts tone and length **[Writer available in both browsers, measured, 00]**. The same recording can feed N6 (test) or a Storybook story (section 5.3).

### N10. Runtime lint, explained

- Prompt: "Anything off on this page?"
- How: deterministic checks over Tier 0 and Tier 1 data, each with an explanation and a suggested fix from the model:
  - `Eager` components. Since Angular 22.0 a component without `changeDetection` is OnPush (`CHANGELOG.md:859`, measured on the spike app), so `Eager` is an explicit opt-out, often left behind by a migration. The finding asks whether the component still needs it;
  - outputs with no template listener (`getListeners`), a heuristic: `getListeners` sees template and host listeners only, so an output subscribed in code shows as unlistened. The finding says that code subscriptions are not visible and asks before suggesting removal;
  - inputs that look unset, a heuristic: no `ng.*` function reports whether a parent template binds an input (02 section 1.2), so the rule flags an input (from `getDirectiveMetadata`) whose current value on the instance is `undefined`. False positives: a parent that binds `undefined` on purpose, and an optional input with no default value. A value equal to the default is not detected at all. The finding is worded as a question **[inferred design]**;
  - `@for` blocks whose `trackExpression` is the item itself on object items (`ɵgetControlFlowBlocks` returns `trackExpression`);
  - zone.js loaded while `NgZone` is `NoopNgZone`: `typeof Zone` is defined in an app that passed the zoneless support check (the last `NgZone` provider record is `NoopNgZone`, 3.3 and 3.4). The zone.js polyfill is then a leftover, and the fix is to remove it. Zone.js apps never reach this rule, because the support check refuses them first **[inferred design]**. Tier 1, through `ɵgetInjectorResolutionPath` and `ɵgetInjectorProviders`. Angular warns about this case only when the app calls `provideZonelessChangeDetection()` (`zoneless_scheduling_impl.ts:370-381`); an app that is zoneless by default gets neither the warning nor the `NgZoneless` mark **[measured in source]**, and the insurance portal is such an app with zone.js loaded (3.4) **[measured, `research/raw/zone-mode-portal.json`]**. A Tier 0-only version can fire only on the explicit-provider case (the `NgZoneless` mark with `typeof Zone` defined), which the console warning already reports **[inferred]**;
  - a11y basics on interactive component hosts (role, name, keyboard reachability), from the roles and names the page agent computes from the DOM (2.2);
  - component metadata rules from the skill (06 rows 14, 16, 17, 18, 20), Tier 0 through `getDirectiveMetadata` and the constructor name: a class name ending in `Component` (shown to the model without the dev-build leading underscore, 05 S3), input names that collide with DOM properties, output names that collide with native events, output names that start with `on` followed by a capital letter, and `ViewEncapsulation.None`;
  - the router audit from the skill (06 rows 21-23, ranked second among 06's ideas): a wildcard route that is not last, eager routes that could be lazy, routes without a title. Tier 1 through `ng.ɵgetRouterInstance` (router trio, `provideRouter` apps only).
- Rule source: the official `angular/skills` repo (`angular-developer` skill, about 34 rules; 11 checkable at runtime, 14 partly, 9 source-only **[counted; classification inferred, 06]**). Of its 11 runtime-checkable rules, N10 takes rows 14, 16, 17, 18 and 20 (metadata) and 21-23 (router audit); row 1 (OnPush, which 06 notes is not a rule in the skills) is the basis of the `Eager` check, and `Eager`'s fix text is Claude's too, because the skill has no OnPush rule; it can point to the CLI MCP server's `onpush_zoneless_migration` tool (06 row 1); row 13 (resource status) is covered by N14; row 32 (`withDebugTracing`) is left out. The other checks in the list (outputs with no template listener, inputs that look unset, `@for` tracking on the item, zone.js loaded while `NgZone` is `NoopNgZone`, a11y basics) are Claude's own and have no skill row; for them the fix text is Claude's, and `get_rule` returns that text **[inferred design]**. The skill's whole reference set is about 34K tokens, so it cannot sit in a 7-9K window. The extension ships a rules table `{id, check, message, fix}` with fix text taken from the skill where a skill row exists, and a `get_rule {rule}` tool (3.4) that returns one rule in at most 150 tokens when the model explains a finding **[measured byte count, 06; token sizes estimated at 4 characters per token]**. The skills declare `license: MIT` in their frontmatter (no LICENSE file in the repo), so bundled text keeps the MIT notice and Google's copyright line **[measured, 06; not legal advice]**.
- Tier 0 and 1. Prompt API with structured output (finding schema), then explanation.

## 6. Ecosystem features

Detection is by global, URL, DOM marker, directive class name, or token name in injector provider records, never by importing the tool's classes **[inferred, 04 section 0]**.

Reading values, not only detecting: a provider record holds the token and the provider definition, not the instance (`ProviderRecord`, 3.4), so the values this section reads come from one of two places **[inferred design]**:
- An instance the page already holds: a component field (from `ng.getComponent`) or a directive instance (from `ng.getDirectives`). This constructs nothing and is the first choice.
- `injector.get` with the token object from a provider record (2.2). For a `providedIn` token, the record appears only on the first `get`, which also creates the instance, so a later `get` on that record returns the existing instance. For a token listed in a `providers` array, the record exists before construction, so `get` can run the constructor **[inferred from `r3_injector.ts:345-362` and `:493`]**. The record alone does not tell the two apart, because both emit the class as the provider **[inferred from the same lines]**. So each `get` below says which case it relies on, and a `get` that can construct asks for a confirm first, as a write does (3.5).

### 6.1 NgRx Store and SignalStore

- Detection and data: a MAIN-world shim for `window.__REDUX_DEVTOOLS_EXTENSION__` installed at `document_start`. `provideStoreDevtools()` reads that global in a provider factory and then sends every action and state through it (`provide-store-devtools.ts:34-45`, `extension.ts:178-276` **[measured]**). `@angular-architects/ngrx-toolkit`'s `withDevtools` connects SignalStores through `window.__REDUX_DEVTOOLS_EXTENSION__.connect` and sends action names with state **[measured from source, 04 section 1.2]**, so the same shim should capture that traffic too **[inferred, 04 section 1.2]**. Caveat: the toolkit docs say `withDevtools` activates only after the user opens the "NgRx Signal Store" tab in Redux DevTools, so the shim may receive nothing until it imitates that step (spike S6). If the real Redux DevTools extension is installed, the shim forwards to it so both work **[inferred, spike S6]**.
- Without devtools providers: SignalStore state is readable by scanning store instances (found as component fields, section 6 intro; no `injector.get`) for the own symbol whose description is `STATE_SOURCE` (dev mode only, `state-source.ts:14-16` **[measured]**); polling gives sampled history. `STATE_SOURCE` is not exported from `@ngrx/signals`' public entry point, so this scan is Tier 1 (third-party) (2.2).
- Features:
  - "Explain this action trace": last N actions with state diffs; the model points to the action that changed the unexpected slice.
  - "Turn this trace into a reducer test": recorded actions and before/after state are a ready fixture (pairs with N6).
  - Anti-patterns from traces: actions that change nothing, action storms, non-serializable state.
  - Natural-language dispatch: the model proposes `{type, payload}` from observed action shapes; the developer confirms.
- Tier: 0 with the shim if the app has `provideStoreDevtools` or `withDevtools` (common in dev); Tier 1 (third-party) for the `STATE_SOURCE` scan; Tier 2 otherwise for exact history.

### 6.4 Analog.js

- Detection: only the `/_analog/` URLs identify Analog: server function calls to `/_analog/fn/:id`, and page endpoints under `/_analog/pages/`, or `/api/_analog/pages/` when the app has an API directory **[measured in Analog source, 04 section 2]**.
- `/@ng/component?c=` HMR requests and `/@vite/client` show only a Vite-based dev server (Angular CLI or Analog), so they do not identify Analog. Angular core builds the `/@ng/component?c=` URL (`packages/core/src/render3/hmr.ts:67` on 22.2.x), and the Angular CLI's Vite-based dev server answers it (`ANGULAR_COMPONENT_PREFIX = '/@ng/component'`, `angular-cli/packages/angular/build/src/tools/vite/middlewares/component-middleware.ts:12` on 22.0.x) **[measured in source]**. That the Angular CLI dev server also serves `/@vite/client` is **[inferred: Vite serves its client at that path, 04 section 2]**.
- Features: "route doctor" that explains why a URL 404s or which layout wraps a page, using the router state plus the file-route table from the root-provided `DEBUG_ROUTES` token (found by token name in provider records; `withDebugRoutes()` makes it visible without that lookup) **[inferred, 04 section 2]**. A root-provided token gets an injector record only when something first injects it (`r3_injector.ts:352-358`, 3.4) **[measured in source]**. `withDebugRoutes()` injects it only when its lazy debug page (`__analog/routes`) is opened: the route uses `loadComponent: () => import('./debug.page')` (`packages/router/src/lib/debug/index.ts:12`), and the only `inject(DEBUG_ROUTES)` in Analog's code is `injectDebugRoutes()` (`debug/routes.ts:35-37`), called from that page (`debug.page.ts:114`) **[measured in Analog source]**. So with `withDebugRoutes()` the token gets its record only after someone opens that page, unless app code calls `injectDebugRoutes()` itself, which `@analogjs/router` exports (`packages/router/src/index.ts:24`) **[measured in Analog source]**. Whether an Analog app injects `DEBUG_ROUTES` without it is open (S12). Reading the table needs `get` with the token from the record; `DEBUG_ROUTES` is a `providedIn: 'root'` token (04 section 2), so a record means the table was already built, and that `get` returns it without constructing anything **[inferred, section 6 intro]**. "Slow page" tracing from a page to its server function calls via network timing.
- Tier 0 for network patterns; Tier 1 (third-party) for the `DEBUG_ROUTES` lookup by token name, which reads Analog's internal token through `ɵgetInjectorProviders`; opt-in for `withDebugRoutes()`.

### 6.5 RxAngular

- Detection: directive classes `RxLet`, `RxFor`, `RxIf` via `ng.getDirectives`; `RxState` instances found as component fields; `RxStrategyProvider` by token name **[names measured in source, 04 section 5; runtime detection inferred, because 04 ran nothing]**. - Where the values come from (section 6 intro): `RxState` from instances found as component fields, with no `injector.get`. Strategy names need `get` with the `RxStrategyProvider` token from a provider record. Whether that class is `providedIn: 'root'` was not checked (04 names it as a class only), so that `get` counts as able to construct it and asks for a confirm first **[inferred design]**.
- Caveat: RxAngular's peer range was Angular `^21` when checked, so 22.2 support is unverified **[measured peer range, 04 section 5]**. Lowest priority.
