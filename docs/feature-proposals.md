# AI-assisted Angular DevTools: feature proposals

Date: 2026-10-11, updated 2026-10-12. Author: Claude, for Lars. Status: research and design, nothing built.

## 1. Summary

**Supported apps.** Angular 22.2 in development mode, using these modern features:
- `bootstrapApplication` with standalone components, and `provide*()` functions such as `provideRouter` and `provideHttpClient`;
- zoneless change detection, with OnPush (the 22.0 default);
- signal inputs and queries (`input()`, `input.required()`, `model()`, `viewChild()`, `viewChildren()`, `contentChild()`, `contentChildren()`), `output()`, the `host` property, and `inject()`;
- built-in control flow (`@if`, `@for`, `@switch`, `@defer`, `@let`);
- functional guards, resolvers and interceptors, with `canMatch` for load guards;
- `@Service()` and `@Injectable()` services (Lars's ruling of 2026-10-12, section 8), each as a singleton (`@Injectable({providedIn: 'root'})`, or `@Service()` with `autoProvided: true`, its default: `autoProvided` "Defaults to `true`", `packages/core/src/di/service.ts:59-62`, and `ɵɵdefineService` sets `providedIn: 'root'` unless `autoProvided` is `false`, `di/interface/service.ts:32` **[measured in source, 22.2.x]**) and as a component-level or route-level provider;
- Signal Forms;
- server-side rendering with hydration (`provideClientHydration()`), in development mode with SSR on (`ng serve` running the app's `server.ts`). Measured on the SSR fixture `spikes/ng222-ssr` (Angular 22.2.2, standalone, zoneless), whose `Server`, `Prerender` and `Client` routes each render in their declared mode **[measured, `research/16`; `research/raw/ssr-render-modes.json`]**. The fixture runs `ng serve --no-hmr`, because under HMR Angular loads every `@defer` dependency eagerly and logs NG0751 **[measured, `research/16`, Setup]**. That is a fact about the fixture, not an app requirement; what N5 reads on an app served with HMR was not measured.

Lars's rule (2026-10-12, section 8): a legacy feature that the extension's tools see the same as its modern form keeps working with no flag and is not listed here, and one that they see differently is not supported, and N10 flags it where it can be detected; `research/12` section 2 has the table for every legacy API. `@Injectable` is Lars's one exception: it is listed above as supported (`research/12` I1).

What that table gives, in short:
- A Zone.js app gets a "not supported" notice in the panel instead of a chat. The panel decides this with the zone-mode check in `app_facts` (3.3, 3.4). An app that is zoneless but still loads zone.js is supported; N10 flags the leftover polyfill.
- NgModule apps are unsupported. The panel decides this with the NgModule check in `app_facts` (3.3, 3.4; `research/12` section 2): the app is standalone when some environment injector on the root component's `ɵgetInjectorResolutionPath` has the `ɵgetInjectorMetadata` source "Environment Injector", which only the standalone bootstrap sets (`bootstrapApplication` and `createApplication`, through `create_application.ts:75`; `platform-browser/src/browser.ts:137,163`). An app whose path has no such injector, and has an environment injector named after an NgModule class (`ng_module_ref.ts:63-67`), gets the "not supported" notice. On the standalone portal the path holds `Standalone[_AppComponent]`, then "Environment Injector", then an injector with source `null` **[measured, `research/raw/zone-mode-portal.json`]**; the NgModule case is **[inferred from source; no NgModule app was run]**.
- `@angular/upgrade` (hybrid AngularJS) apps are unsupported (Lars's ruling, section 8). A hybrid app provides `NgZone` itself through `internalProvideZoneChangeDetection` (`packages/upgrade/static/src/upgrade_module.ts:149`, `downgrade_module.ts:386,392`), so it runs Zone.js change detection, and it has an NgModule root. So the zone-mode check and the NgModule check both refuse it, and it needs no check of its own **[inferred: read in source, no upgrade app run]**.
- `RouterModule.forRoot` publishes no router globals **[measured, 02 section 1.1]**, so router features cannot answer. In an NgModule app the NgModule check refuses the app; in a standalone app that imports it through `importProvidersFrom`, N10 flags it.
- Template-driven and Reactive Forms are not supported: the forms feature (N15) reads Signal Forms only, and N10 flags the legacy forms directives.
- Decorator `@Input()` fields and decorator queries are not supported: the signal tools see only signal inputs and signal queries, and N10 flags them. `*ngFor`, `canLoad`, `providedIn: 'any'` and `Eager` components are not supported either, and N10 flags each (N10, legacy rules).

Superseded by Lars's rule (2026-10-12), kept for the record: "Angular 22.2 in development mode, bootstrapped standalone, with zoneless change detection, functional APIs (functional guards, resolvers, interceptors and providers such as `provideRouter`), and Signal Forms (Lars's ruling of 2026-10-12, section 8). Everything else is unsupported, and the design has no second code path for it:
- A Zone.js app gets a "not supported" notice in the panel instead of a chat. The panel decides this with the zone-mode check in `app_facts` (3.3, 3.4). An app that is zoneless but still loads zone.js is supported; N10 flags the leftover polyfill.
- NgModule apps are unsupported. This includes the `RouterModule.forRoot` router setup, which publishes no router globals **[measured, 02 section 1.1]**. The panel has no check that detects an NgModule bootstrap; none was looked for in the evidence (section 9).
- Template-driven and Reactive Forms are unsupported; the forms feature (N15) reads Signal Forms only."

No shipped framework devtools panel uses an on-device model **[inferred from search, 03 section 5]**. Pangular Inspector, Chrome DevTools for agents, agent-react-devtools and the Angular CLI MCP server all hand data to an external cloud or IDE agent; Chrome's own DevTools assistant runs on cloud Gemini and is opt-in under terms of service.

The Angular AI docs contributed five things:
- `overview.md` (the "Build with AI" page at `angular.dev/ai`) is about apps that call cloud models. Its best practices match 3.3 and 3.5: tools that the developer controls, a human in the loop (3.5's confirm before writes), and output constrained by a schema **[documented, Angular AI docs read in 02 section 4.1]**.
- `design-patterns.md` gives one of N2's rules.
- WebMCP support gives N9.
- The Angular CLI MCP server is the code-side complement to this extension (N13).
- `agent-skills.md` names the `angular/skills` repo, which is the rule source for N10 **[documented, 02 section 4.5; rules counted in 06]**.

The AI tutor (`ai-tutor.md`) is a persona for a coding agent. It runs through the CLI MCP server and reads project files **[documented, Angular AI docs read in 02 section 4.4]**. So a port of it, which needs project files and an agent that writes code, has no runtime counterpart in a devtools extension **[inferred]**. N27 (section 4) is a different tutor that needs neither: the learner predicts what the running app will do, acts in it, and code grades the prediction against measured runtime data; it is the runtime counterpart (`docs/design/tutor.md` section 1.1) **[inferred design]**.

Four facts shape the design:

1. **On-device models can drive tools today, but not equally.**
   - Aion-1.1-Instruct (Edge Dev 157) answered all 15 benchmark runs through native tool calls, at 3-6 s per question.
   - Gemma 4 (Chrome Beta 156) is reliable only through a structured-output loop (13/15 runs on the default GPU low tier, 15/15 on CPU, which needs the `OnDeviceModelForceCpuBackend` command-line feature).
   - Gemini Nano also runs on that loop, because in native mode it makes no tool calls at all. On the loop it passed 11/15 runs on GPU and 0/15 on CPU, so it is supported on GPU but not reliable, and unsupported on CPU.
   - Phi-4-mini (Edge stable) is weak at both **[measured, 05; Nano GPU figures regraded with `916fc09`, `spikes/probes/regrade.mjs`]**.
   - The browser never runs tools itself: `prompt()` returns `tool-call` parts, and the extension runs them and sends `tool-response` parts back **[measured, 00 and 01]**.
   - So the extension needs a routing rule. No API in the evidence names the model, so the rule in 3.3 uses what the extension can observe: native tools only on Edge with a `contextWindow` of 7,168 (Aion as measured) and a passing native canary; the structured-output loop everywhere else; unsupported when the structured-output canary fails. It is a heuristic, with a manual override in the panel settings **[inferred from measured per-model results]**. `availability()` cannot tell whether tools work **[measured, 09]**.
2. **The context window is small: 7,168 tokens on Aion and 9,216 on the Chrome models and Phi-4-mini** **[measured, 05]**. A whole page's component details and signal graphs do not fit (05 S3); a bare component list does. The model gets facts by id from small tools that return a short summary; it never receives full output.
3. **Angular 22 already ships two in-page AI tools.** Every dev-mode app answers the `devtoolstooldiscovery` DOM event with `angular:di_graph` and `angular:signal_graph` **[measured, `packages/core/src/debug/ai/registration.ts:21-38`, `platform.ts:48-50`]**. The extension can collect them with one event dispatch and no `ɵ` name (run from the page's main world in S2; from the extension's content script, spike S8). The design uses them only in part: 3.2 never runs `angular:di_graph`, and for the signal graph it either wraps `angular:signal_graph` behind a component id or calls `ng.ɵgetSignalGraph` directly.
4. **Most of what Angular DevTools shows is reachable from `window.ng` in a MAIN-world script** with no app change **[measured, 02 section 1-2]**. The parts that need internals are already on the page in dev mode, mostly as `ng.ɵ*` functions (Tier 1). Real Tier 2 gaps at 22.2 are small: `@if`/`@switch` block state, template local refs, the DI event stream **[measured, 02 section 1.3 and 5.7]**, and error-boundary state **[inferred from absence: no boundary hook in `global_utils.ts` or `control_flow_types.ts`, 02 section 5.6]**. The error-boundary gap means that `ng` exposes no boundary API. N16 tries a Tier 0 route around it, which its spike must confirm.

Recommended first release, in priority order:

| # | Feature | Why it is new | Tier |
|---|---|---|---|
| N1 | "Why did this update?" change-detection causality | Angular DevTools shows timings; it does not follow the chain through signals to each component. In a zoneless app that signal chain is the only record of what caused the cycle | 1 (Decision 1: allowed) |
| N2 | Signal provenance and reactive anti-pattern finder | The signal graph pane draws nodes; it does not trace or judge | 1 (Decision 1: allowed) |
| N3 | DI doctor | Explains resolution failures and duplicate instances in prose | 0 + 1 (Decision 1: allowed) |
| N4 | Angular error explainer | On-device Console Insights that knows `NG0xxx` and the owning component | 0 |
| N24 | Zoneless stale-view finder | The page shows the old value while the instance holds the new one, and no panel says why; N24 finds the plain field written in a `subscribe` callback and names the modern Angular pattern | 1 (Decision 1: allowed) |
| N25 | RxJS interop explainer | The signal graph pane draws `toSignal.source` and an unlabelled effect; N25 says which interop call made them and that the graph stops at the Observable | 1 (Decision 1: allowed) |

N6 was removed by Lars's ruling of 2026-10-12; the first release has six features (N1 to N4, N24 and N25); N6 has no replacement.

N1, N2, N3, N24 and N25 use Tier 1 (`ng.ɵ*` functions already on the page). The brief asks to avoid Tier 1. Lars ruled on Decision 1 in section 8 on 2026-10-12: Tier 1 is allowed, labelled and feature-detected. The Tier 0-only first release listed under Decision 1, led by N4, N10's Tier 0 rules and N11, stays there for the record.

Stretch (app opt-in): N9, agent rehearsal for WebMCP tools. It tests whether a small model can use the app's own tools, so it works only on apps that register WebMCP tools. The brief calls that a stretch: "using WebMCP in the Angular application may be considered a stretch prerequisite".

Stretch (Tier 2, app opt-in): a subscription inspector that lists a component's open RxJS subscriptions. RxJS is a private module bundled into the app, so the page has no handle on its subscriptions unless the app re-exports a hook to `globalThis` **[inferred]**.

Plus a chat panel that promptifies every Angular DevTools tab (section 5), and ecosystem adapters led by an NgRx Redux DevTools shim (section 6).

API details that the implementation must follow **[measured, 00 and 01]**:

- `create()` with `tools` needs both `expectedOutputs: [{type:'text'}, {type:'tool-call'}]` and `expectedInputs: [{type:'text'}, {type:'tool-response'}]`, or it throws.
- Tool calls arrive as `LanguageModelToolCall` objects with getter fields `name`, `callID`, `arguments`. `JSON.stringify` shows `{}`. The member is spelled `callID`; `callId` throws.
- Results go back as `new LanguageModelToolSuccess({callID, name, result: [{type:'object', value}]})` (or `LanguageModelToolError`) inside `{role:'user', content:[{type:'tool-response', value}]}`, immediately after the call. Prompting without a response fails with `kErrorUnknown`.
- Model quirks to code around:
  - Gemma 4 returns `callID: ""`. Pass it back unchanged.
  - Gemma 4 fails tool prompts with `kErrorUnknown` on camelCase tool names without underscores such as `getComponentCount`, while `get_component_count` works **[measured, S1 phase 2, 11]**. The rename changed case and underscores together, and the two were not separated (11; spike S11).
    - Answered (2026-10-12, S11): an uppercase letter in the tool name is what fails. On the Gemma 4 instance (Chrome Beta 156.0.8078.17, GPU low tier), one fresh session per variant, 70 s apart: `get_component_count` with a required `scope` returned a tool call with `{"scope":"page"}`; `get_component_count` with empty `properties` returned a tool call with `{}`; `getcomponentcount` (lowercase, no separator) returned a tool call with `{"scope":"page"}`; `getComponentCount` and `Get_component_count` failed with `kErrorUnknown` **[measured, n=1 per variant, `research/raw/tool-name-matrix-gemma4-gpu.json`]**. So missing underscores do not fail, and an empty `properties` schema does not fail **[measured, n=1 per variant; inferred that it generalises]**. A doctor run right after passed every canary, so the two crashes did not disable the model **[measured]**. Gemma 4 on CPU, Nano, Aion and Phi-4-mini were not run on the matrix.
  - Chrome disables the on-device model after three crashes without a successful response in between; a successful response resets Chrome's count **[measured, Chromium 156 source, 11]**. On Gemma 4, the camelCase `kErrorUnknown` failures were model-process crashes **[measured, 11]**; that the two S11 failures were crashes too is **[inferred: same error on the same instance]**. Chrome re-enables the model after 1 minute at the third crash, and the wait doubles per further crash, up to 1 hour **[measured, Chromium 156 source, 11]**.
  - Whether other `kErrorUnknown` errors count toward that limit is **[inferred]**, not checked. The same code also comes back in cases with no camelCase name:
    - for a prompt sent after an unanswered tool call (Aion, 00);
    - in Edge benchmark runs (Aion fallback 1, Phi-4-mini 3), where Chromium's crash counter is not known to apply;

  - The object is page data like `window.ng`: any page script can replace it, so the extension trusts it no more than it trusts `window.ng`.

### 3.2 One tool registry, four sources

Every capability is a tool with `{name, description, inputSchema, execute}`. The Prompt API shares `{name, description, inputSchema}`: its declarations have no `execute`, because a per-tool `execute` (closed loop) is not yet in the specification or in browsers **[documented, 01: the explainer calls it "a planned future extension"]**. The registry keeps `execute` for the page agent, which runs each tool call. Angular's `ToolDefinition` (`primitives/devtools/src/tool_definitions.ts`), WebMCP and the chrome-devtools-mcp third-party tools API use the same name, description and schema, so one registry serves all four sources in the table below. App WebMCP tools keep the names the app chose, so they do not go to every model session: N9 says which sessions get them **[inferred design]**.

The evidence:
  - On a one-component 22.2 app the tool's output is 42,788 characters.
  - It calls `injector.get(ViewContainerRef)` on component hosts. After that, `ng.ɵgetSignalGraph` (and `angular:signal_graph`) lose the template node and the signals that only the template reads (`title`, `double`, `items`), for the rest of the page's life. `count` stays, because the effect also reads it (05 measured `effect, signal:count` afterwards). A draft upstream report is in `filing-ledger.md`.
  - `ɵgetDependenciesFromInjectable`'s first statement is `injector.get(token, null, {self: true, optional: true})`, and it throws "Unable to determine instance of ..." when that returns null (`packages/core/src/render3/util/injector_discovery_utils.ts:61-63` on the 22.2.x branch) **[measured in source]**. That is the call shape that breaks the signal graph for `ViewContainerRef` (05 S2).
  - On an environment injector, the same `get` constructs a provided service that was not created yet and runs its constructor **[inferred from `R3Injector.get` (`r3_injector.ts:323`, record creation at 352-358) and `hydrate` (`:529-537`); not run]**.
  - After that first `get`, the function also calls `get` for each of the class's dependencies along the resolution path (`{self: true, optional: true}` on each injector until one returns a value, and for a `host` dependency a second `get` on the first injector with the dependency's own flags instead of `self: true`; `injector_discovery_utils.ts:85-125`) **[measured in source]**. Each dependency was resolved when the instance was built, so for a class that is known to be constructed these calls return existing instances **[inferred]**.
  - Pangular avoids the same trap: its injector view "skips uncreated services to avoid instantiating them" (03 section 1.3, Injectors row) **[documented, Pangular docs at `76c09d0`, 03]**.
- `angular:signal_graph` takes `{target: HTMLElement}`, which a model cannot produce, and its description alone is 1,390 characters. The registry wraps it behind a component id from `find_components` and a short description, or calls `ng.ɵgetSignalGraph` directly. N2's write rules always call `ng.ɵgetSignalGraph` directly, because `angular:signal_graph` strips `debuggableFn` (02 section 1.5).
- `angular:di_graph`'s definition has an empty `properties` schema and a namespaced name (`angular:di_graph`), and neither is known to be safe on Gemma 4 (see 2.1). So even its definition is not passed through unchanged. (Updated 2026-10-12, S11: an empty schema passed on Gemma 4 GPU, and the name has no uppercase letter, so it meets the naming rule; a name with a colon was not tested **[measured for the schema, n=1; the colon untested]**.)

The extension's own tool group, answered through `devtoolstooldiscovery` for chrome-devtools-mcp users, follows the same rules and holds only MAIN-world read tools (3.5). Whether it is published next to Angular's group is unchecked (above, S8).

### 3.3 The model loop

Before any of the steps below, the panel runs `app_facts` once per page load. It runs two support checks (3.4): the zone-mode check and the NgModule check. If the zone-mode check reads Zone.js change detection, the panel shows a "not supported: this panel supports zoneless apps only" notice; if the NgModule check finds no environment injector with the source "Environment Injector" on the root component's path, it shows a "not supported: this panel supports standalone apps only" notice. In either case it creates no model session and runs no other tool **[inferred design]**. A zoneless app that loads zone.js passes the zone-mode check. An `@angular/upgrade` hybrid app fails both (section 1) **[inferred]**.

1. **Intent and tool subset.** A fresh clone of a warm session gets the question and a list of tool groups, and returns `{groups: [...]}` under `responseConstraint`. Only those groups' tools go into the next session. Small models choose worse among many tools, and every tool schema costs context **[inferred; tool count per session is a spike, S3]**.
2. **Tool session.** `create({tools, expectedInputs, expectedOutputs, initialPrompts: [system, context chip]})`. The context chip is a short line naming what the user has selected (a component or element) and the app facts from N18, shown in the panel and sent as context. The chip shows nothing about zone mode: every app that reaches the chat passed the zoneless support check above **[inferred design]**. Loop: `prompt` -> run each `tool-call` in the page agent -> send `tool-response` -> repeat, with a step cap (Chrome's own assistant caps at 20 **[measured in DevTools source, 01]**; start at 6 for a 7K window **[inferred]**).
3. **Structured-output loop.** Used where `tools` is missing or ignored (Chrome 154 stable with the flag off), and wherever the routing rule below chooses it. The same loop runs on structured output.
   - The model returns `{"tool": name, "args": {...}}` or `{"answer": "..."}` under a `responseConstraint` built from the tool schemas.
   - Tool results are appended as text.
   - Neither the API nor `create()` tells whether tools work. Chrome 154 accepted `tools` silently and never called them **[measured, 00]**.
   - Chrome Beta defines `LanguageModelToolCall` and `LanguageModelToolSuccess` and accepts a tool session. Yet its tool prompts failed with `kErrorUnknown` in 00's probes **[measured, 00]**, the same symptom that S1 phase 2 measured as a model-process crash (11) **[inferred for 00]**. 00 blamed tools with no parameters. That cause is confounded, and the camelCase tool name alone reproduces the crash (see the quirks in 2.1) **[measured, 11]**. S11 then showed that an uppercase letter in the name is the trigger and that an empty schema works on Gemma 4 GPU (2.1) **[measured, n=1 per variant]**.
   - So run the startup check (both canaries on Edge, the structured-output canary alone on Chrome) when the panel opens and no cached result matches the key (below) **[inferred design]**:
     - Native canary: one round trip with a `ping` tool and "Call ping.". The canary follows the naming rule of every other tool (3.4, 3.6): `ping {scope: {enum: ['page']}}`, lowercase. It keeps one required parameter although the rule no longer asks for one (2.1), because that is the shape of the S11 control that passed on Gemma 4 GPU, and a canary that also returns an argument checks the `arguments` getter that every later tool call depends on **[inferred design]**. It passes if a `tool-call` part comes back and the follow-up prompt succeeds. A pass does not by itself choose native tools; the routing rule below does.
     - The native canary runs only on Edge. On Chrome the routing rule sends the model to the structured-output loop whatever the native canary says, so its result cannot change the route there, and a `kErrorUnknown` from it could add a crash toward Chrome's three-crash limit (2.1). A native tool session on Chrome comes only from the manual override, which does not consult the canary **[inferred design]**.
     - Structured-output canary: a one-step prompt under a small `responseConstraint`. If the reply is empty or is not valid JSON, the fallback loop cannot run on the model, so the routing rule below marks it unsupported unless it goes to native tools. Nano on the CPU backend is the measured case: its fallback failed 15 of 15 runs, 14 with empty or cut-off JSON (2.1). The extension cannot read the backend (2.1), so this check is how it finds out. One of those 15 runs returned valid JSON, so a single passing reply is not enough: repeat the canary three times and require all three **[inferred from the 14 of 15 rate]**.
     - The check runs without blocking the chat and stops at the first failure (one failure already marks the model unsupported). A question asked before the check finishes uses the cached result when one matches the key; with no cached result it runs on the structured-output loop, the route of every supported model except Aion, which also passed 11/15 on it (2.1). If the check then marks the model unsupported, that answer is stopped and replaced by the unsupported message. When the manual override is set, it decides, as always **[inferred design]**. A passing result runs once per cache key (below); an unsupported result is checked again (below) **[inferred design]**. The reason is its cost on Nano CPU:
       - In `research/raw/bench/nano.json` the fallback questions have medians of 34-42 s per question **[measured]**.
       - 14 of the 15 failed runs threw on the JSON parse (`SyntaxError: Unexpected end of JSON input`), and the harness saves such runs with `calls: []` from its catch block, so their calls are not recorded (`bench.js:168`); the 15th answered in text with no tool call **[measured]**. So that each failed run was a single prompt is **[inferred]**.
       - Three repeats could hold the panel for about two minutes at first open (three repeats at 34-42 s are 102-126 s); the canary's schema is smaller than the benchmark's, so that is an upper bound **[inferred]**.
     - The fallback's `responseConstraint` part is measured to work on Gemma 4 (GPU and CPU), Aion, Phi-4-mini and Nano on GPU, and to fail on Nano on CPU **[measured, 05]**.
   - Cache the canary results (two on Edge, the structured-output result alone on Chrome) under a key of user agent and `contextWindow`, and check again in two cases: a loop reply that comes back empty or as invalid JSON runs the structured-output canary again, and a cached unsupported result is checked again at each panel open **[inferred design]**. The reasons:
     - The key notices only a major-version change or a window change. Every saved benchmark run records a reduced user agent with no build number (`Chrome/156.0.0.0` on Chrome Beta, `Chrome/157.0.0.0 Edg/157.0.0.0` on Edge Dev, `Chrome/155.0.0.0 Edg/155.0.0.0` on Edge stable; `ua` field of `research/raw/bench/*.json`) **[measured]**, and the key cannot tell Nano from Gemma 4 or a GPU backend from a CPU backend.
     - Keying on the browser version, or on the user agent, is not enough on its own: the Nano and Gemma 4 instances are both Chrome Beta 156.0.8078.17 with `contextWindow` 9,216 (00, 05), and Nano's backend follows the stored performance class, which Chrome measures at startup (00, "Choosing CPU or GPU per instance"), so the same version can move Nano from GPU (fallback 11/15) to CPU (0/15). That the class changes between startups on one machine is **[inferred]**, not observed.
     - An empty or invalid JSON reply is the measured Nano CPU symptom, so running the canary again on it catches the move from GPU to CPU.
     - The reverse move, from CPU back to GPU, produces no loop reply to react to, because an unsupported model runs no loop. So while unsupported is the cached result, each panel open runs the structured-output canary once more in the background (it stops at the first failure), the "unsupported" message has a "Check again" control, and the message points to the manual override (routing rule below) **[inferred design]**.
   - **Routing rule [inferred from measured per-model results]**, applied in this order; the first bullet that applies decides:
     - Native tools when the browser is Edge, `contextWindow` is 7,168 (Aion as measured; Phi-4-mini on Edge stable reports 9,216) and the native canary passes. The structured-output canary does not decide this case.
     - Otherwise, the structured-output loop, if the structured-output canary passes three times out of three.
     - Otherwise (the structured-output canary failed), the model is unsupported (Nano on the CPU backend).
     - No API in the evidence names the model: 2.1 lists what the browsers do not tell, and the model names in 00 come from manifests and `on-device-internals`, which the extension cannot read. So the rule is a heuristic. An Edge update can change the window or the model and break the 7,168 test. The panel settings give the user a manual override: native tools, structured-output loop, or automatic. Spike S13 looks for an in-API signal that tells the models apart.
   - **After a `kErrorUnknown` on Chrome, do not retry automatically [inferred design].** The extension stops the question, shows the error, tells the user that Chrome may count it toward its three-crash limit (2.1), and prompts again only when the user retries. It also keeps its own count of these errors and shows it with the error. The count resets on any successful prompt, as Chrome's count does (2.1). It is a lower bound: the extension cannot see crashes caused by other pages or extensions. The reasons:
     - Chrome disables the on-device model for the whole browser after three crashes with no successful response between them, and a retry loop could reach that limit by itself (2.1).
     - Snake_case names with a required parameter do not prevent the error: the Gemma 4 benchmark run in 2.1 followed that rule and still failed **[measured, `research/raw/bench/gemma4.json`]**.
     - 3.6's "retry once on a tool error" covers a tool that returns an error, not a failed session, so it does not apply here.

   Why `availability()` cannot decide this:
   - In Chrome 156 the tool types are gated by the Blink runtime feature `AIPromptAPIToolUse`, not by the model. With the feature off, `create()` refuses any `tool-call`/`tool-response` type with "unable to create a session". `availability()` still says `available`, because it never checks tool types, which contradicts the spec **[measured: probe matrix 05, Chromium 156.0.8078.17 source 09]**.
   - With the feature on, Gemini Nano opens tool sessions but answered with text instead of a tool call in all three tries **[measured, 05]**. In the benchmark, none of Nano's 15 native GPU runs made a tool call. Nano's native passes (2/15 GPU, 1/15 CPU) made no tool call **[measured, `research/raw/bench/nano-gpu.json`, `nano.json`]**, so they are grader artifacts: two are code-text answers to question 1 that passed its number check (where the "2" sat is **[inferred]**, because saved answers are cut at 160 characters), and one is an untooled guess (2.1). No Google source claims tool calling for Nano **[measured by search and page reads, 10]**.
   - So the routing rule above gives, as in 2.1: Aion, native tools; Gemma 4, Gemini Nano and Phi-4-mini, the structured-output loop; Nano on the CPU backend, unsupported. Native tools on Gemma 4 only after S4 improves tool choice and argument accuracy and S13 finds a way to tell Gemma 4 from Nano.
   - Microsoft documents Aion 1.0 Instruct as a text model; no source describes Aion-1.1-Instruct, the version Edge Dev 157 serves. Its tool calls come from Edge's runtime workaround (`msEdgeLLMOnDeviceModelMuffinToolUseWorkaround`), so they can change with an Edge update **[documented, 10; the link between the workaround and Aion measured, 00: the flag's description in Edge Dev 157 names "the on-device Aion model family"]**.
4. **Answer rendering.** Answers show the tool walkthrough (each call, its arguments, a short result, a Reveal link to the element, the component in the tree, or the source), as Chrome DevTools AI assistance does **[documented, 03 section 3.1]**. The walkthrough is what makes a small model's answer checkable.
5. **Context budget.** `contextoverflow` fires after the API has already evicted the oldest prompt and response pairs **[documented, 01 section 1]**, and that eviction removes the user's question before old tool results (07 section 4). So the trigger for summarizing is a budget check before the window fills: before each `prompt()`, call `measureContextUsage()`, and if the result would leave less than about 1,000 tokens free, summarize the conversation with the Summarizer API (available in both browsers **[measured, 00]**) into a new session's initial prompts **[inferred, 07 section 4]**. `contextoverflow` is only a fallback: on it, rebuild the session from the panel's own transcript **[inferred design]**.

### 3.4 Core tool set

Designed after Pangular's agent tools and React DevTools' lazy detail protocol **[documented: Pangular docs at `76c09d0` and React DevTools, 03 sections 1.5 and 2.2]**: a small tree with ids, details on demand, hard output caps with "N more, narrow with X" messages, and stable ids from a `WeakMap`.

**Tools take ids, not selectors.** `find_components` returns short ids (`c3`), and every tool that targets a component takes `{id}`. The evidence **[measured, counted from `research/raw/bench/*.json`; table and counting rule in 2.1]**:
- Bad arguments (an invented CSS selector, a signal name in the selector field, or a wrong signal name) caused 3 of Aion's 4 fallback failures, 3 of Phi-4-mini's 8 fallback failures, 2 of Gemma 4 GPU's 2 fallback failures, 3 of Nano GPU's 4 fallback failures, 2 of Gemma 4 GPU's 7 native failures and 3 of Gemma 4 CPU's 6 native failures (2 of them invalid selectors that made the harness throw). Ids remove the selector part of that class. Code repairs most of the rest before the tool runs (argument repair, 3.6).
- Signal names are checked against `list_signals` (below), but that check catches only names that do not exist. A real but wrong signal (`count` for a question about `double`, 2 of Nano GPU's 4 fallback failures) passes it. That is a question-understanding error, which ids and lists do not address.
- A second class, choosing the wrong tool or stopping after one call without an answer, caused 4 of those 7 Gemma 4 GPU failures, the other 3 of Gemma 4 CPU's 6 native failures and 3 of Phi-4-mini's 8 fallback failures. Ids do not address it; S4 does.

The names in the table are the names the model receives. Every argument that names something takes a value that a list tool returned or an `enum`, and every tool checks its arguments itself, on every model **[inferred design]**. The details:
- The names follow the rules in 3.6: lowercase names (snake_case recommended for readability), no optional parameters, and no free-text arguments. A tool with nothing to ask may take an empty `properties` schema; the earlier rule of at least one required parameter (`scope: {enum: ['page']}`) was relaxed after S11 (2.1). `set_writable_field.value` is the one argument whose content the model writes; the tool checks it against the field's current type (table) **[inferred design]**.
- Where each value comes from: `id` from `find_components`; `signal` is a signal label from `list_signals`; `token` is a token name from `di_path`'s list or from the error message that N4 captured (a `NullInjectorError` names the missing token, which is on no provider record and so never in `di_path`'s list); `field` is the name of a writable signal field or a plain field, both from `inspect_component`. `inspect_component` finds writable signal fields with Tier 0 calls: a field whose value passes `ng.isSignal` and has a `set` method, which is the test Angular's own `isWritableSignal` makes (`packages/core/src/render3/reactivity/api.ts:55-57`) and Angular DevTools applies before a write (`property-mutation.ts:93-99`) **[measured in source; its use here inferred design]**. So `set_writable_field` does not depend on `list_signals` (Tier 1) and stays in the Tier 0-only release.
- Tools are fixed at `create()` (07 section 2), so where the set of values is known when the session is created (component names, rule ids), the argument is an `enum`. Where it is not (the signal labels of a component found later), the argument is a string that the tool checks against the list tool's output, and a miss returns the error template with up to 10 valid values (3.6). Aion probably does not enforce `enum`s (inferred in 3.6), so that check runs on every model **[inferred design]**.
- `di_lookup` checks `token` against both sources: a name in neither `di_path`'s list nor a captured error message returns the error template; a name from an error message that is on no provider record along the path returns the no-record answer (next paragraph), not an argument error **[inferred design]**.

**`di_lookup` answers from provider records, not from `injector.get`** **[inferred design]**:
- It walks the `ɵgetInjectorResolutionPath` path and reads `ɵgetInjectorProviders` on each injector; the first injector whose records hold the token is where it resolves, unless injection flags or view-provider visibility say otherwise (next bullet).
- Limits of that walk: it ignores injection flags (`@Self`, `@SkipSelf`, `@Host`, `@Optional`), which change where a dependency resolves, and it does not apply `viewProviders` visibility. A record marked `isViewProvider` (02 section 1.2) is visible only inside its component's own view, not to content projected into it (06, `hierarchical-injectors.md`), so for a projected child the walk can name a parent's view provider as the source. So the walk skips `isViewProvider` records on an injector whose view does not contain the asking node, the answer is worded "resolves here unless injection flags say otherwise", and for the classes on the host, `ɵgetDependenciesFromInjectable`'s answer (which reads each dependency's own flags, 3.2) is used instead of the walk **[inferred design]**.
- When no record on the path matches, it answers "no provider record on this path; a `providedIn: 'root'` token gets a record only when it is first injected", never a flat "not provided".
- It calls `ɵgetDependenciesFromInjectable` only with `instance.constructor` of a component or directive on the host, never for a service token or a node-injector special token.
- `di_path` drops the six special tokens from the token names it gives the model.

The evidence:
- Neither `ɵgetInjectorResolutionPath` nor `ɵgetInjectorProviders` instantiates anything (3.2).
- A missing record does not prove that the token is not provided: an `R3Injector` creates the record for a `providedIn` token, and emits the provider-configured event that `ɵgetInjectorProviders` reads, only the first time something calls `get` for that token (`packages/core/src/di/r3_injector.ts:352-358` on 22.2.x) **[measured in source]**. So a `providedIn: 'root'` service or token that nothing has injected yet is on no record. 6.4 and spike S12 describe the same case for Analog's `DEBUG_ROUTES`.
- `ɵgetDependenciesFromInjectable` calls `injector.get` for the class and for each of its dependencies along the path (3.2), so it is safe only on a token that is known to be constructed on that injector. The only such tokens are the component and directive classes on the host, which the tool gets as `instance.constructor` of an instance from `ng.getComponent` or `ng.getDirectives` on that element. Angular DevTools calls it the same way (`instance.constructor`, `devtools/projects/ng-devtools-backend/src/lib/directive-forest/component-tree/component-tree.ts:155-158, 340`) **[measured in source]**.
- No `ɵ` function reports whether a service on an environment injector has been constructed (`ProviderRecord` has `token`, `isViewProvider`, `provider` and `importPath` only, `render3/debug/injector_profiler.ts:129-149`) **[measured in source]**, hence no service tokens.
- `getNodeInjectorProviders` appends six tokens registered with `registerSpecialProvider` to every node injector's records (`injector_discovery_utils.ts:219-229`): `Injector`, `ChangeDetectorRef`, `Renderer2`, `ViewContainerRef`, `DestroyRef` and `ElementRef` **[measured in source, 22.2.x]**. Getting `ViewContainerRef` this way breaks the signal graph (05 S2, measured); the other five left it intact or were not tested (`filing-ledger.md` section 1).

**Tools answer the narrow question; the page agent reads the graph.** In S2, given the raw signal graph (nodes plus edges by index), Aion named the wrong dependencies for `double` and Gemma 4 named the right ones **[measured, 05]**. In the earlier two-tool probe, Gemma 4 misread a flat input value and Aion did not **[measured, 00]**; that was not an index-linked structure. From one run each, neither model can be trusted to read index-linked structures, so no tool returns one **[inferred]**.

### 3.5 Safety rules

- Reads run without asking. Writes (`set_writable_field`, navigate, dispatch, form fill) and every WebMCP call, including ones marked `readOnlyHint`, because the hint comes from the app, pause for a confirm button in the panel, as Chrome's assistant and Pangular's `confirm: true` do **[documented for Chrome, 03 section 3.1; documented for Pangular, Pangular docs at `76c09d0`, 03 section 1.5]**.
- A read-only switch drops all write tools from the registry.
- The confirm labels a write that can leave the page (a form submit, an NgRx `dispatch` whose effect calls the server, an app WebMCP call) as "may change server data"; the small models' argument errors (2.1) make the exact call on the confirm screen the only guard **[inferred design; Lars's decision 3]**.
- The tool group that the extension publishes through `devtoolstooldiscovery` (3.2) holds only tools whose `execute` runs entirely in the page's MAIN world on data the page can already read (`ng.*`, the DOM). It holds no write tool and no tool that uses extension privileges: not `page_snapshot` (`chrome.tabs.captureVisibleTab` returns the pixels of the whole visible tab, including cross-origin iframes the page cannot read), nothing through `chrome.*` or `chrome.devtools.*`, and no data captured from other frames. Two kinds of caller can reach that group without the user: an external MCP client while the panel is closed, and any script on the page, because `devtoolstooldiscovery` is a plain DOM event that any page script (or another extension's MAIN-world script) can dispatch, after which it can call each returned `execute` directly (02 section 1.5; 03 section 3.3) **[inferred design]**.
- Every model output that reaches the user passes a deterministic code-shape check first, in every feature, not only N27: no fenced block and no line that looks like code (an assignment, an arrow, a semicolon at line end, or a call with arguments in backticks longer than a name). An output that fails is not shown and not retried (Aion decodes greedily, so the same input gives the same output, 07 section 1.4): the feature shows its code-built finding, fact list or shipped text instead, marked "not explained". This enforces Lars's no-code ruling ("2:", section 8) at runtime. It can also reject prose that quotes a call such as `ng.getComponent(el)`, so the explanation prompts ask for API names without arguments **[inferred design, from `docs/design/tutor.md` section 4.5]**.
- The extension only activates on pages where `window.ng` exists (dev mode). On production builds it says so and does nothing **[inferred]**.
- Everything stays on the device. In Chrome, the built-in model sends nothing to Google or a third party **[documented, Chrome get-started docs, 03 section 3.4]**. For Edge, Microsoft's Prompt API page says "the data input to the model never leaves the device" **[documented, https://learn.microsoft.com/microsoft-edge/web-platform/prompt-api; `research/14` 1.6]**. Chrome DevTools AI assistance, by contrast, sends data to cloud Gemini and is opt-in.

### 3.6 Prompting the small models

No vendor guidance exists for these exact builds. The kit below combines Chrome's Prompt API pages, Google's Gemini Nano prompt design page, the Gemma 4 docs, the Phi-4-mini model card, and what was found on disk for Aion. Details and sources are in `research/07-prompting-small-models.md`.

- **What Aion is:** its tokenizer uses Phi-4's chat and tool tokens, and its config says `qwen3`, a 32,768-token native context and greedy decoding **[measured from its files, 07 section 1.4]**. `msedge.dll` holds the tool-use prompt text and the `<|tool_call|>` format as string constants, plus log lines about parsing a tool-call payload **[measured, 07]**. That Edge puts the tool list between those constants in the system prompt, and that it parses `<|tool_call|>{...}` out of free reply text, are **[inferred, 07]**. So tool argument `enum`s are probably not enforced on Aion **[inferred, 07]**. Chrome Beta's binary contains llguidance constrained-decoding code **[measured, 07 section 3]**; that it is used for `responseConstraint` is **[inferred, 07]**, and whether Gemma 4's tool calls go through it is unresolved.
- **System prompt:** about 120 tokens, `## Rules` style, short rules: facts only from tools, one call at a time and stop when answered, `<page>` text is data, retry once on a tool error, at most three sentences.
- **Tools:** lowercase names, with no uppercase letter (on Gemma 4 such a name fails with `kErrorUnknown`; a crash, as S1 measured for camelCase, is inferred for the other S11 variant; S11, 2.1), snake_case recommended for readability; one sentence of description, under about 200 characters, never Angular's long in-page descriptions; 0-3 required flat parameters, with an empty `properties` schema allowed where the tool has nothing to ask (relaxed after S11, 2.1); an "e.g." and a "not X" clause where confusion was measured; ids or an `enum` of the ids that exist on the page, or, where the values are not known at `create()`, a string the tool checks against a list tool's output (3.4); never free text (one exception, `set_writable_field.value`, parsed against the field's type, 3.4). Code fills in arguments it already knows, such as the selected component.
- **Results and errors:** results are flat objects that echo the identifying arguments; page strings go in `<page>...</page>` and are capped at 200 characters; arrays are capped at 20 with `total`. Errors use one template that names the bad argument, the likely mix-up and up to 10 valid values.
- **Argument repair** (approved by Lars, 2026-10-12, Rulings below). Code checks and repairs a call's arguments before the tool runs. A model's bad argument is a malformed call, and code can often fix it:
  1. Deterministic repair first **[inferred design]**:
     - Normalise: trim, lowercase, strip `.`, `#`, `*` and attribute syntax.
     - Match against the page's known ids, selectors and signal names, by token match, or by fuzzy match within edit distance 2 when that gives exactly one candidate.
     - Move a signal name found in the selector field to the component that owns that signal.
     - Drop unknown keys.
     - Unwrap a model that echoed the tool's schema.
     - Replay of the saved benchmark runs (`spikes/probes/arg-repair-replay.mjs`, output `research/raw/arg-repair-replay.json`, commit `a2c654f`): 131 tool calls, 26 with invalid arguments, 21 of those made valid by the repair **[measured]**. Not repaired: `signal: "*"` (2 calls), `"[ + ]"`, `"increment"` (a method, not a signal) and the invented class `.app-counters-double-increment`.
  2. Constrained built-in AI fallback, only for calls the deterministic step cannot repair **[inferred design]**:
     - One small Prompt API call with `responseConstraint`. Its input is the user's question, the bad argument, and the valid options as an enum. Its output is one valid id or `none`.
     - Code validates the result again. The model picks among real options; it never decides validity.
     - On `none`, the error template above and one retry apply.
     - Cost: one extra prompt, about 3-6 s on Aion and 11-14 s on Gemma 4 GPU, judged from the measured per-question medians **[inferred]**.
  3. Never repair writes. A write runs only with exact arguments, behind the confirm (3.5) **[inferred design]**.
  4. Show it. The walkthrough shows every repaired call and what changed **[inferred design]**.
  5. Per-prompt enum on the structured-output loop: its `responseConstraint` gets an enum of the ids on the page, built fresh for each prompt, so invented names cannot occur. Native tool sessions cannot do this, because their schemas are fixed at `create()` **[inferred design]**.
  6. Limits:
     - Validation catches malformed calls, not misunderstood questions. Nano's valid-but-wrong `signal: "count"` passes validation.
     - The replay counts validity, not answer correctness.
     - The other built-in APIs do not fit this job, and there are no embeddings, so similarity stays in code.
  7. Spike S19 (section 7) reruns `bench.js` with the repair step on. Not run.
- **Fallback loop guards in code:** if the model repeats a call or reaches step max-1, re-prompt with an answer-only schema. With greedy decoding, Aion reproduces the same call from the same context, so this guard is required **[inferred, 07]**.
- **Experiments E1-E13** (07 section 6.5) cover selector confusion, the repeat loop, empty schemas, declaration cost, result shape, injection and sampling; none has run yet. E1-E10, E12 and E13 can run on the existing benchmark harness, which runs in a page tab (05). E11 (sampling) needs an extension context, such as the S1 extension, because `temperature` and `topK` exist only in extensions (07 sections 1.1 and 6.5). They are the next benchmark round. The Phi-4-mini and Gemini Nano baselines they waited for are now in 05.

### 3.7 Deterministic code first

Lars's request (verbatim, 2026-10-12): "Generally for our design and feature proposals, we should consider how browser built-in AI APIs can be combined with normal, deterministic TypeScript/JavaScript, especially to mitigate the small context windows, for example to process graphs in chunks or offload deterministic computations to the main thread rather than Prompt API or other browser built-in AI APIs, or to Workers if that is possible in a DevTools web (browser) extension." Details and sources are in `research/15-deterministic-and-ai.md`.

**Principle [inferred design].** Code computes every fact that has an algorithm (counts, diffs, rule checks, graph walks, epoch comparisons), and the model receives only what code cannot do: choose among candidates, explain a finding, write prose. One question takes a median of 2-34 s on the supported configurations and the window is 7-9K tokens (2.1) **[measured]**, while the deterministic work at the measured page sizes (at most 892 signal nodes and 54,597 characters of compact graphs on one portal route, 05 S3 **[measured]**) is small for JavaScript **[inferred; not timed]**. "Deterministic part" in each feature (section 4) says what code computes and what the model receives.

**Patterns (`research/15` section 2) [inferred design unless marked]:**

| Pattern | What stays in code | What the model receives (measured sizes where the evidence has them) |
|---|---|---|
| Pre-computation | counts, path diffs, rule checks, graph walks, before any prompt | a finding of under 100 tokens plus at most 150 tokens of rule text, not the data it came from **[inferred]** |
| Graph slicing around one node | k-hop producers and consumers by node index, library-internal nodes dropped, labels in the output only | the portal's `ng-journal-create` graph is 13,878-25,838 characters (107 nodes, 171 edges); the one-hop slice around its template is 230 characters **[measured, Claude's count over `research/raw/tosignal-node-portal.json`]** |
| Chunked map-reduce | the split (first dedupe: 47 components on `/contract/list` are 9 classes, 05 S3 **[measured]**), the merge, every cross-chunk relation | chunks of at most 2,000 tokens, each in a fresh clone under a `responseConstraint`, then at most one summary call over the merged result |
| Summarizer with a deterministic outline | headings, order, ids, names and numbers | only the free-text parts (stack traces, console text, long recordings); `inputQuota` and `measureInputUsage()` exist **[documented, writing assistance explainer]**; the quota on these builds is not measured (S15) |
| Tool results capped by code | the caps of 3.4 and 3.6, tightened per session with `measureContextUsage()` | one result of a few hundred tokens |
| Argument repair | normalising and matching a call's arguments against the page's known ids, selectors and signal names (3.6); 21 of 26 invalid calls in the saved runs **[measured]** | only for a call code cannot repair: the question, the bad argument and an enum of valid options, one prompt, answer one id or `none` |
| Structured output validated by code | value checks (ids, rule ids, labels); on an invalid or empty reply the finding is shown from the rules table, marked "not explained", with no retry loop | nothing extra; a bad reply costs one explanation, not the finding |
| `clone()` from a warm base | which base to clone (one per tool subset; a map base with no tools) | a clone starts from the base's few hundred tokens; cold `create()` 3.3-21 s, warm 2-3 ms (00) **[measured]**; `clone()` itself not timed (S15) |
| Cache keyed by graph epoch | key from component id, node ids and each node's `epoch` (`ɵgetSignalGraph` nodes carry it, 02 section 1.2 **[measured in source]**) | nothing on a hit; plain fields are no graph node, so features that read them add the field values to the key |

**Execution contexts, short form (`research/15` section 1) [measured for the rows S1 ran, 11; others as marked]:**

| Context | A long task blocks | Reads `ng.*` | Built-in AI | Use |
|---|---|---|---|---|
| Page MAIN world | the page | yes, the only one | yes (S1) | read and shape `ng.*` data; small checks on one component |
| Isolated content script | the page | no | yes (S1) | relay; JSON from here on in Chrome **[documented, Chrome message passing docs]** |
| DevTools panel, side panel | that panel; whether also the other extension pages is not checked (S14) **[inferred]** | no | yes (S1) | session host, merge, group, cache |
| Service worker | its own events; cannot start a `Worker` **[documented, MDN]**; stops after 30 s idle **[documented]** | no | yes (S1) | routing and per-tab state only |
| Offscreen document | its own document, sharing as for the panel (S14) | no | yes (S1) | worker host when no panel is open (`WORKERS` reason **[documented]**) |
| Dedicated or shared worker from an extension page | nothing outside the worker **[documented for workers]** | no | not run; yes as read in Chromium `main` source **[documented in source; S14]** | recordings, traces, page-wide text and source scans; the chunk loop if S14 passes |
| Worker from a content script or the page | nothing outside the worker | no | no as read: web workers are excluded **[documented, Prompt API explainer]** | not used |

Every value that leaves the MAIN world is shaped there first: `ɵgetSignalGraph` nodes carry `debuggableFn` functions, which the structured clone cannot copy **[documented, MDN]**, and Chrome's extension messaging uses JSON **[documented]** **[inferred design]**.

**Limits (`research/15` section 3).** An open question over the whole page has no known split or merge; the panel answers it from code (a list of findings) and the model explains the finding the user picks **[inferred design]**. Every chunk is a prompt: 47 prompts on `/contract/list` would take 2.4-4.7 min on Aion and 8.6-11 min on Gemma 4 GPU at the measured per-question medians **[inferred multiplication of measured medians]**, so a chat answer uses at most about five prompts, and a larger job runs as a background job with progress, or the code-only answer replaces it **[inferred design]**. More prompts also mean more chances of `kErrorUnknown` toward Chrome's three-crash limit (3.3) **[inferred]**.

### N1. "Why did this update?" change-detection causality

- Prompt: "Why did `app-cart` re-render when I typed in the search box?"
- How: `cd_record` subscribes through `ng.ɵsetProfiler`. Per cycle it records the event that started it (output listener, DOM listener via `getListeners`, signal write seen as a template consumer epoch change, `applyChanges`, timer). Per component, it records whether the template ran and which bound signals changed epoch. The model gets the fact list of one cycle, the one the question names (picked by code, 3.7), and explains the chain: "the `input` listener on `app-search` set `query`, `app-cart` reads `filteredItems`, which is computed from `query`, so its template ran" **[inferred; event list measured in `packages/core/primitives/devtools/src/profiler_types.ts:22-156`]**. The event list has no timer event; the only listener event is `OutputStart`, which `listeners.ts:90` fires for template and host listeners **[measured in source, 22.2.x]**. So a timer or another trigger that is not a listener is named by elimination (a `ChangeDetectionStart` with no `OutputStart` before it) **[inferred]**. N1 does not read the zone task, even when zone.js is loaded: a zoneless app can load zone.js, as the insurance portal does (3.4, `app_facts`) **[measured, `research/raw/zone-mode-portal.json`]**, and in such an app the zone task did not start the cycle **[inferred]**.
- Adds over Angular DevTools: its profiler shows time per component and flame graphs. It does not follow the chain from a trigger through signals to each component that was checked; N1 adds that per-component chain, which a zoneless app (the 22.x default and the only supported kind) has no other record of. Note: Angular DevTools fills a frame's "Source" from `Zone.currentTask.source` whenever zone.js is loaded (`ng-devtools-backend/src/lib/profiling/capture.ts:373-379`) **[measured, Angular DevTools source on the 22.2.x branch]**; in a zoneless app that loads zone.js it likely names the zoneless scheduler's timer or microtask, not the trigger (`util/callback_scheduler.ts:54-59`, `zoneless_scheduling_impl.ts:218-223`) **[inferred from that source; not run]**. Pangular's change-detection recorder shows recent cycles with the triggering output listener **[documented, Pangular docs at `76c09d0`, 03 section 1.3]**; it does not explain them with a model. This is React DevTools' "Why did this render?" applied to Angular's signal and zoneless model **[documented, 03 section 2.1]**.
- Legacy forms (`research/12` section 2): N1 follows only signal inputs and signal queries (a decorator `@Input()` or query change is no signal epoch change, `research/12` C1, C3), and it explains an `Eager` component's check as "checked because `Eager`", with no signal cause (`research/12` D3).
- Deterministic part: code records the cycles, picks the cycle the question names (the last cycle that checked the named component), names the trigger (`OutputStart`, or a timer by elimination), and walks the graph from each signal whose epoch changed to the templates that read it, so the chain is computed, not inferred by the model. The model receives that one chain as a fact list of about 5-10 lines (an estimate of 150-300 tokens) **[inferred]**, never the recording. A question over a recording ("what keeps re-rendering?") is grouped by code: cycles with the same chain become one line with a count, capped at 20 lines (3.7) **[inferred design]**. A long recording is kept and grouped in a worker (3.7) **[inferred design]**.
- Tier 1 (`ɵsetProfiler`, `ɵgetSignalGraph`). Prompt API with tools.

### N2. Signal provenance and reactive anti-pattern finder

- Prompts: "Where does the value of `total` come from?", "Is anything in this component an effect that should be a computed?"
- How: `signal_trace` walks producers from a node back to writable sources; the model narrates the chain with labels (labels come from compiler-inserted `debugName`, `implicit_signal_debug_name_transform.ts` **[measured, 02 section 5.3]**). A deterministic rule pass over the graph, plus a source-text scan for writes (below), flags patterns, and the model explains each finding by naming the modern Angular pattern and why the flagged use is an anti-pattern, with no code written for the app (Lars's ruling of 2026-10-12, section 8):
  - an `effect` whose only job is to write another signal (prefer `computed` or `linkedSignal`);
  - a cycle or an effect that writes a signal it reads (possible loop);
  - a `resource` whose params read a signal that changes per keystroke (the `design-patterns.md` advice on separate input and submitted signals, `design-patterns.md:5-39` **[measured]**);
  - unlabeled nodes (suggest a `debugName`, Solid devtools idea **[documented, 03 section 4.6; from a search summary, not a page read]**). An effect created without assignment, as in the counter app's constructor (`effect(...)` as a bare statement in `spikes/ng222-app/src/app/counter.ts`), has an empty label (05); one assigned to a variable or a field, or with `this.x = effect(...)`, gets its name from the compiler, because the transform covers those three cases for `effect` and `afterRenderEffect` (`implicit_signal_debug_name_transform.ts:127-210`, `:224-238`; 02 section 5.3) **[measured in source]**. So this rule skips effects, and findings name an effect by its label when it has one, otherwise by its owning component and its source text **[inferred design]**.
- How the write rules see writes: the signal graph alone cannot see them. `ng.ɵgetSignalGraph` has read edges only, and a signal that nothing reads is not a node. On `spikes/ng222-app` the effect that writes `lastLogged` appears only as `effect -> signal:count` **[measured, `spikes/probes/effect-writes.js`, `9959d32`, 05]**. The profiler events include no effect runs either **[measured in source, 05]**. The route that works: each effect node keeps `debuggableFn`, and its source text there is `() => this.lastLogged.set(this.count())`, in which a scan for `.<name>.set(` and `.<name>.update(` found `lastLogged.set` **[measured, same probe]**. The scan reads `ng.ɵgetSignalGraph` directly, because `angular:signal_graph` strips `debuggableFn`, and it needs Angular 22.1.3 or later, when non-computed nodes got the field (02). It is a heuristic **[inferred]**: writes made through a called method or another object, writes without `this.`, and minified code were not tested and can be missed. Findings from these two rules say so.
- Rule detection is code; the model only explains the finding, names the modern Angular pattern and says why. That keeps findings deterministic while the prose adapts to the component **[inferred design choice]**.
- Wording rule: design docs, the panel, prompts and code all say "modern Angular pattern" (Lars's ruling of 2026-10-12, section 8), never "ordained" or "blessed".
- Legacy forms (`research/12` section 2): provenance and the pattern rules see only signal inputs and signal queries; decorator inputs and queries are not graph nodes (`research/12` C1, C3).
- Deterministic part: the rule pass, the `debuggableFn` scan and the `signal_trace` walk are code (above). The model receives one finding at a time (rule id, component, node label, one line of evidence, under 100 tokens) plus the rule's text from `get_rule` (at most 150 tokens), or for provenance the trace as one line per hop **[inferred]**, never the component's graph: on the portal's `/claim/create` that graph is 13,878-25,838 characters, about 3,500-6,500 tokens, against 230 characters for the one-hop slice around its template **[measured characters, Claude's count over `research/raw/tosignal-node-portal.json`; tokens inferred]**. Several findings are grouped by rule, with one explanation per rule in its own clone (3.7) **[inferred design]**.
- Tier 1. Prompt API with tools and structured output (findings schema: rule, node, severity, pattern, why).

### N3. DI doctor

- Prompts: "Why do `ProductList` and `ProductDetail` get different `CartService` instances?", "Where would `AUTH_CONFIG` resolve from here?"
- How: `di_path` plus `di_lookup` for both components, then a diff of the two resolution paths. Both read provider records along each path and construct nothing; `ɵgetDependenciesFromInjectable` runs only on the component's own class (3.4). The model explains which injector provides each instance (component `providers`, route environment injector, root) and names the modern Angular pattern for the outcome the question asks about (for one shared instance, `providedIn: 'root'` or one provider on a common ancestor) and why, with no code written for the app (Lars's ruling of 2026-10-12, section 8). The answer carries `di_lookup`'s limit: injection flags such as `@SkipSelf` or `@Host` on the injecting class can move the real source, and the walk does not see them (3.4) **[inferred design]**. For `NullInjectorError` caught by N4, it reconstructs the path at the failing component and passes the token name from the error message to `di_lookup`, which reports "no provider record on this path" (3.4). For "Where would `AUTH_CONFIG` resolve from here?" the same answer is worded with its caveat: a `providedIn: 'root'` token that nothing has injected yet has no record, so the model says that the token may still resolve at root once it is first injected, not that it is missing (3.4) **[inferred design]**.
- For a question about the whole app, it runs `di_path` and `di_lookup` over the relevant components. It never runs `angular:di_graph`, which section 3.2 forbids.
- Legacy forms (`research/12` section 2): N3 does not support `providedIn: 'any'` tokens, which get one instance per lazy environment injector (`research/12` I2); constructor injection and `inject()` give the same answers (`research/12` C5), so they need no note.
- With the opt-in export (2.2): for a class on the vetted list (for example `Meta`), N3 matches records by identity and can say "provided at root, not created yet" where it now says "no provider record on this path"; it still constructs nothing. Tier 2 (app opt-in); the Tier 1 record route stays the default, and the app's own services are never on the list **[inferred design]**.
- Deterministic part: code computes both resolution paths, the first injector where they part, and which injector holds the token's record on each side. The model receives that diff (two short injector chains and the providing injector on each side, an estimate of about 200 tokens) **[inferred]**, never the provider lists, which hold about 99-124 environment providers per path **[measured, 05 S3]**. For a question about the whole app, code runs `di_lookup` per component and groups the components by providing injector; the model receives the grouped table, capped at 20 rows (3.7) **[inferred design]**.
- Tier 0 (`getInjector`) plus Tier 1 (injector functions). Prompt API with tools.

### N4. Angular error explainer (on-device Console Insights for Angular)

- Trigger: an uncaught error or `console.error` containing `NG0` / `NG0xxxx` codes, or a click on "Explain" in the panel's error list.
- How: the page agent hooks `window.onerror`, `unhandledrejection` and `console.error`, keeps the stack and the element if the error carries one, and maps it to a component with `ng.getOwningComponent`. The model gets: error code, message, the component's inputs and listeners, and the matching entry from a bundled offline digest of `angular.dev/errors` (shipped with the extension, no network). It answers "what happened, in this component, and what the error page says resolves it", with no code written for the app (Lars's ruling of 2026-10-12, section 8).
- The digest's source: the angular repo's `adev/src/content/reference/errors` on the 22.2.x branch, 61 `NG*.md` pages (plus `overview.md` and a `BUILD.bazel`), 95,095 bytes in all, about 24K tokens at 4 characters per token; the largest page is 4,758 bytes (`NG0991.md`), about 1,200 tokens **[measured byte count; token sizes estimated]**. The repo's `LICENSE` is MIT, with Google LLC's copyright line **[measured; not legal advice]**. The whole set cannot sit in a 7-9K window, so the digest stores one entry per code, cut to at most 150 tokens when the extension is built, as `get_rule` caps a rule (N10), and only the matching entry goes to the model **[inferred design]**. The digest as shipped in the extension keeps the MIT license and the copyright notice, so the license terms are met **[inferred; no license review was done]**. Code strips the notice from every entry before any text goes to the Prompt API or another built-in AI API (Lars's ruling of 2026-10-12, section 8) **[inferred design]**.
- Adds over Chrome Console Insights: Console Insights' full explanation runs on cloud Gemini under opt-in **[documented, 03 section 3]**; its short "teasers" already run on-device through the Prompt API (`BuiltInAi.ts`) **[measured, 01]**. N4 adds Angular error codes, the owning component and its inputs and listeners, and a full explanation on-device.
- Deterministic part: code captures the error, maps it to the owning component, looks up the digest entry by code (at most 150 tokens, against about 24K tokens for all 61 pages) **[measured bytes; tokens estimated, above]**, and trims the stack to the app's own frames, dropping framework and `node_modules` frames and capping the rest **[inferred design]**. The model receives the code, the message, the component's capped inputs and listeners (3.6), the digest entry and the trimmed stack. Only a stack that is still over the budget after trimming goes through the Summarizer, inside an outline that code builds (3.7) **[inferred design]**.
- Tier 0. Prompt API with tools; Summarizer for long stacks.

### N5. Hydration and `@defer` doctor

- Prompts: "Why is the reviews block still on its placeholder?", "Why did hydration skip `app-map`?"
- How: `defer_blocks` gives each block's state, triggers and incremental hydration state; `hydration_status` gives the hydration counters and, per mismatched component, the expected and actual node. The model correlates triggers with what happened (for example an `on viewport` trigger on an element that is never visible, or a `hydrate never` block). This is React DevTools' "suspended by" applied to `@defer` **[documented, 03 section 2.3]**.
- What the page shows, run on the SSR fixture `spikes/ng222-ssr` (`research/16` sections 1, 2 and 7):
  - `defer_blocks`: before the trigger, `ng.ɵgetControlFlowBlocks` returns the block with `state: "initial"`, `incrementalHydrationState: "dehydrated"` and `triggers: ["hydrate on interaction", "on idle"]` (the implicit `on idle` main trigger is listed); after one click, `state: "complete"` and `incrementalHydrationState: "hydrated"` **[measured, `research/raw/ssr-defer.json`]**.
  - Correction: `defer_blocks` carries no timings. A block reports only its configured `minimumTime` (placeholder and loading block) and `afterTime` (loading block), not when it loaded or hydrated **[measured, `research/raw/ssr-defer.json`]**. So N5 can say which trigger a block waits for, not how long it took; a duration would need the page agent to time the state change itself **[inferred]**.
  - Counters: six `ngDevMode` counters (`hydratedNodes`, `hydratedComponents`, `dehydratedViewsRemoved`, `dehydratedViewsCleanupRuns`, `componentsSkippedHydration`, `deferBlocksWithIncrementalHydration`) **[documented in source, `research/16` section 1]**. On a clean page they read 40 nodes and 4 components, and they keep counting after the first hydration: `hydratedComponents` went from 4 to 5 when the `@defer` block hydrated **[measured, `research/raw/ssr-hydration.json`, `research/raw/ssr-defer.json`]**. Angular logs the same numbers in one console line after hydration **[measured, `research/raw/ssr-hydration.json`]**.
  - Per-node status: `__ngDebugHydrationInfo__` is a DOM expando `{status}` with `hydrated`, `skipped` or `mismatched` **[documented in source, `research/16` section 1]**; on a clean page 34 nodes carry it, all `hydrated` **[measured, `research/raw/ssr-hydration.json`]**.
  - Correction: a mismatch is recorded on the closest component host (`<app-mismatch>` in the fixture), not on the node that differs. The entry holds `expectedNodeDetails` and `actualNodeDetails`, strings that mark the location ("`<p>…</p>  <-- AT THIS LOCATION`" against a `<div>`), and `ng.getComponent` on the host names the class **[measured, `research/raw/ssr-hydration.json`, `?mismatch=1`]**. So `hydration_status` reports mismatches per component, not per node. The page shows one console error (NG0500, with the expected and actual DOM and the component name) and no overlay; the app keeps running, and `hydratedNodes` drops from 40 to 32 **[measured, same file]**. N4 sees the NG0500 error through its console hook **[inferred]**.
  - Correction: a text-only difference never shows. With `?mismatch=text` the server sends `server text`, the page ends with `client text`, and there is no error and no non-hydrated node **[measured, `research/raw/ssr-hydration.json`]**. Hydration matches nodes by type and tag, so text and attribute differences are overwritten without a trace **[inferred, `research/16` section 2]**. N5 says so when asked about one.
  - The "skipped" case ("Why did hydration skip `app-map`?") rests on the `skipped` status and the `componentsSkippedHydration` counter, which are documented in source **[documented in source, `research/16` section 1]** but not exercised: the fixture has no `ngSkipHydration`, and the counter read 0 on every page **[measured, `research/raw/ssr-hydration.json`]**.
- Prior art: Pangular's component view already lists `@defer` blocks with state, triggers, hydration state and "hydrate never" **[documented, Pangular docs at `76c09d0`, 03 section 1.3]**, and its tool output goes to an external agent. New here: an on-device model correlates the triggers with what happened, and the app installs nothing.
- Deterministic part: code reads `defer_blocks` and `hydration_status`, keeps only blocks that are not in their final state and components with a mismatch or a skip, and checks the correlations that have a rule (an `on viewport` trigger whose element has no box in the viewport, a `hydrate never` block, an expected node against the actual one). The model receives one fact line per remaining block or component, capped at 20, and explains the cause **[inferred design]**.
- Not reachable: a mismatch caused by server-only code (the fixture's `<div>` depends on `REQUEST`) shows only as its effect; the server code that caused it, and `REQUEST` itself, stay on the server (section 9). `__ngDebugHydrationInfo__` and `ngDevMode` are page JavaScript state, so only the MAIN-world page agent reads them **[inferred, `research/16`]**.
- Tier 1 (`ɵgetControlFlowBlocks`, with a support statement; `__ngDebugHydrationInfo__` and the `ngDevMode` counters, with none). Prompt API with tools.

### N9. Agent rehearsal for WebMCP tools (stretch: app opt-in)

- Prompt: "Can an agent use my app's tools to add an item to the cart?"
- How: when the page exposes `document.modelContext` (flag `enable-webmcp-testing`, active in Chrome Beta and Edge Dev after a relaunch; `document.modelContext` exposes `registerTool`, `getTools`, `executeTool` and `toolchange`/`toolactivated`/`toolcancel` events **[measured, 00]**), the extension lists the app's tools (Chrome documents `getTools()` / `executeTool()` for extensions **[documented, 01]**) and runs the on-device model as the agent against them. It reports where the model failed: an unclear description, a schema that allows bad input, a form tool blocked by a field the model cannot fill, a missing `readOnlyHint` on a read. A small model failing is a useful signal: a cloud agent will do better, but the same descriptions confuse it too **[inferred]**.
- Fallback when the browser has no `document.modelContext`: a MAIN-world shim at `document_start` that provides `registerTool`, so Angular's `declareExperimentalWebMcpTool` registers into the extension (Angular registers only if `registerTool` exists, `declare_tool.ts:35-46` **[measured]**). The shim must not install itself when a native implementation is present.
- Which model sessions get the app's tools: the app's tools keep the names, descriptions and schemas the app chose, so they need not follow 3.6's naming rule, and names with an uppercase letter failed with `kErrorUnknown` when they reached Gemma 4's native tool declarations (2.1) **[measured, 11, S11]**; a crash, as S1 measured for camelCase, is **[inferred]** for `Get_component_count`. So app tools go unchanged to Aion's native tools and to the structured-output loop on any model, where tool names reach the model only as text in a JSON schema. A native tool session on Chrome, which only the manual override can select (3.3), gets the app tools whose names have no uppercase letter and leaves out each app tool whose name has one; the panel names the tools left out and says that they need the automatic route or the structured-output loop there **[inferred design]**. Renaming app tools to lowercase for that session and mapping the name back on the call was not chosen, because N9 tests the app's own names, and a renamed tool would test a name the app does not use **[inferred design]**.
- WebMCP tool audit (`research/14` C11, folded in by Lars's ruling of 2026-10-12, section 8; it replaces EXT4). Prompt: "Are my app's tools ready for an agent?" Deterministic rules over `getTools()`, run before and without a rehearsal **[inferred design]**:
  - a name outside the spec's character set (ASCII letters and digits plus `_`, `-` and `.`, at most 128 code points) **[measured, WebMCP `index.bs`, `research/14` 3.1]**, or over Chrome's recommended 30 characters **[documented, Chrome's secure-tools page, "subject to change", `research/14` 3.1]**;
  - an uppercase letter in a name: such a tool cannot reach a native tool session on Chrome (S11, above);
  - a description over Chrome's recommended 500 characters **[documented, same page]**, or over the extension's 200-character cap outside N9 (3.6);
  - a parameter without a description; a tool with no annotation at all;
  - a read with no `readOnlyHint` (EXT4's rule). The annotations to check are `readOnlyHint`, `consequentialHint` and `untrustedContentHint`; the spec has no `destructiveHint` or `idempotentHint`, and its fourth hint, `debugging`, is missing from Angular's `Annotations` interface **[measured, `index.bs` and `types.ts:64-84`, `research/14` 3.1]**;
  - a tool still registered after the user leaves its route, detected as a tool still listed by `getTools()` after a navigation that `router_state` reports **[inferred, `research/14` 3.2]**;
  - duplicate names: the spec rejects them with `InvalidStateError` **[measured, `index.bs`, `research/14` 3.1]**, and Angular's guide tells developers to expect a throw **[documented, `research/14` 3.4]**.

  The model explains each finding and names the modern Angular pattern and why: register tools from root services or with `provideExperimentalWebMcpTools`, never from a component constructor that renders more than once, because a second registration of the same name throws; route tools only with `withAutoCleanupInjectors()`, because otherwise the tool outlives its route (Angular's WebMCP guide, https://angular.dev/ai/webmcp) **[documented, `research/14` 3.3]**. No code for the app (Lars's ruling of 2026-10-12, section 8). Data: `getTools()` and `router_state`. Prompt API with structured output (finding schema), then explanation. Tier: app opt-in, plus Tier 1 for the route rule (`router_state`).
- Deterministic part: the audit above is code, and so are these checks of each app tool's declaration before any model run: a free-text parameter where an `enum` fits, and a missing `required`. Those are findings with no model; the model receives one audit finding at a time (rule, tool name, one line of evidence) and explains it. Code also notes which names a Chrome native session must leave out (above); that is a limit of the session, not a finding about the app. The model runs only the rehearsal, with the app's declarations as written; if they do not fit the window with the rehearsal's budget (`measureContextUsage()`), code splits the tools into groups and rehearses each group in its own session (3.7) **[inferred design]**.
- Tier: app opt-in (the app must use `provideExperimentalWebMcpTools`, `declareExperimentalWebMcpTool` or Signal Forms `experimentalWebMcpTool`). Prompt API with tools (or the structured-output loop, above). Pangular shows WebMCP form tools **[documented in Pangular's `inspectors/forms.md`, with its `forms-webmcp.ts` read in source, 03 section 1.5]** but does not test them with a model (no model API in its source) **[measured, 03 section 1.5]**.

### N10. Runtime lint, explained

- Prompt: "Anything off on this page?"
- How: deterministic checks over Tier 0 and Tier 1 data. The model explains each finding: it names the modern Angular pattern and why the flagged use is an anti-pattern or not supported, and writes no code for the app (Lars's ruling of 2026-10-12, section 8):
  - `Eager` components (`research/12` D3: not supported, flagged). Since Angular 22.0 a component without `changeDetection` is OnPush (`CHANGELOG.md:859`, measured on the spike app), so `Eager` is an explicit opt-out, often left behind by a migration. The finding says that the component is not supported: it is checked on every cycle, so N1 can explain its checks only as "checked because `Eager`", with no signal cause. It names the modern Angular pattern, OnPush (the default since 22.0, so no `changeDetection` at all), and why: the zoneless guide calls OnPush "a recommended step towards zoneless compatibility" **[documented, `research/12` D3]**;
  - outputs with no template listener (`getListeners`), a heuristic: `getListeners` sees template and host listeners only, so an output subscribed in code shows as unlistened. The finding says that code subscriptions are not visible and is worded as a question;
  - inputs that look unset, a heuristic: no `ng.*` function reports whether a parent template binds an input (02 section 1.2), so the rule flags an input (from `getDirectiveMetadata`) whose current value on the instance is `undefined`. False positives: a parent that binds `undefined` on purpose, and an optional input with no default value. A value equal to the default is not detected at all. The finding is worded as a question **[inferred design]**;
  - `@for` blocks whose `trackExpression` is the item itself on object items (`ɵgetControlFlowBlocks` returns `trackExpression`). It checks `@for` only; a `*ngFor` is not supported and gets the legacy rule below (`research/12` T2);
  - zone.js loaded while `NgZone` is `NoopNgZone`: `typeof Zone` is defined in an app that passed the zoneless support check (the last `NgZone` provider record is `NoopNgZone`, 3.3 and 3.4). The zone.js polyfill is then a leftover; the finding names the modern Angular setup, a zoneless app with no zone.js polyfill, and why: the polyfill patches browser APIs that nothing in a zoneless app uses **[inferred]**. Zone.js apps never reach this rule, because the support check refuses them first **[inferred design]**. Tier 1, through `ɵgetInjectorResolutionPath` and `ɵgetInjectorProviders`. Angular warns about this case only when the app calls `provideZonelessChangeDetection()` (`zoneless_scheduling_impl.ts:370-381`); an app that is zoneless by default gets neither the warning nor the `NgZoneless` mark **[measured in source]**, and the insurance portal is such an app with zone.js loaded (3.4) **[measured, `research/raw/zone-mode-portal.json`]**. A Tier 0-only version can fire only on the explicit-provider case (the `NgZoneless` mark with `typeof Zone` defined), which the console warning already reports **[inferred]**;
  - a11y basics on interactive component hosts (role, name, keyboard reachability), from the roles and names the page agent computes from the DOM (2.2);
  - component metadata rules from the skill (06 rows 14, 16, 17, 18, 20), Tier 0 through `getDirectiveMetadata` and the constructor name: a class name ending in `Component` (shown to the model without the dev-build leading underscore, 05 S3), input names that collide with DOM properties, output names that collide with native events, output names that start with `on` followed by a capital letter, and `ViewEncapsulation.None`;
  - the router audit from the skill (06 rows 21-23, ranked second among 06's ideas): a wildcard route that is not last, eager routes that could be lazy, routes without a title. Tier 1 through `ng.ɵgetRouterInstance` (router trio, `provideRouter` apps only).
- Legacy rules, from Lars's rule of 2026-10-12 (section 8): one rule for each legacy form that the tools see differently from its modern form and that a page can reveal (`research/12` section 2, outcome "not supported; N10 flags it when detected"). Legacy forms that the tools see the same get no rule. Each finding names the legacy use, the modern form (the modern Angular pattern), why the extension's tools see the legacy form differently, and the migration schematic from `research/12`'s Migration column where one exists, with no code written for the app (Lars's ruling of 2026-10-12, section 8), and gives the component's file and line from `constructor.ɵcmp.debugInfo`, the `ɵsetClassDebugInfo` part of the class-metadata channel (`research/12` section 0.2, read on the counter fixture's live page **[measured]**). None of the detections below has been run:
  - `*ngFor` (`research/12` T2): `ng.getDirectives` on the anchor comments in a component's view returns an `NgForOf` (class name with any leading underscore stripped) **[inferred from source: `ng.getDirectives` skips only Text nodes, `discovery_utils.ts:202-225`, and the anchor comment carries patch data, `render3/instructions/template.ts:104`]**. Modern form: `@for` with `track`. Schematic: `ng generate @angular/core:control-flow-migration`. Tier 0, plus Tier 1 for file and line. The reason it differs: the `@for` tracking rule above reads `ɵgetControlFlowBlocks`, which lists `@for` blocks only, so it cannot check a `*ngFor`.
  - Decorator `@Input()` (`research/12` C1): for each input that `ng.getDirectiveMetadata` lists, the instance property fails `ng.isSignal` **[inferred]**, Tier 0; the class metadata confirms the field: `propDecorators[field][0].args?.[0]?.isSignal` is not `true` **[`isSignal: true` measured on the counter's `input()`; the `@Input()` shape inferred]**, Tier 1. Modern form: `input()`, `input.required()` or `model()`. Schematic: `ng generate @angular/core:signal-input-migration`.

- N22: code parses the `provideStabilityDebugging()` console lines into pending tasks and groups them by source. The model receives the grouped list, capped at 20 sources.

- N27: code finds each lesson's live example, builds the answer options, records what the app did and grades the prediction. - N28: the rules are code: a dead click is a click after which no change-detection cycle, DOM mutation or navigation follows within 300 ms (S17); a rage click is the same target clicked three or more times within two seconds (`research/14` C8). - N31: code reads `ng.ɵgetTransferState(ng.getInjector(<root>))`, which re-reads `<script id="ng-state">` and leaves out Angular's hydration keys (`__nghData__`, `__nghDeferData__`) **[documented in source, `research/16` section 3]**. Code keeps `u`, `s`, `st`, `rt` and the body size, drops the body, and counts the Resource Timing entries whose URL matches `u` resolved against the page URL. It classifies each URL by the measured cases **[measured, `research/raw/ssr-transfer.json` and the fixture's server log]**: an entry and 0 Resource Timing entries is a cache hit (the server render made the one request); no entry on a server-rendered page and 1 Resource Timing entry is a request the server did not cache (`?transfer=0`: the server log shows two hits, the server render and the browser); no `ng-state` script at all and 1 Resource Timing entry is a client-rendered route (`/client`). Prompt API with tools. Not reachable: whether the server render also made a request it did not cache, which is the second run in "ran twice", is only in the server log; requests the server did not cache (POST, requests with auth headers, `transferCache: false`) leave no trace in `ng-state` (section 9). - N32: all of it is code. Under `ng serve` the prerendered route is rendered per request; what a production server sends for a route prerendered at build time was not measured, so a production `ssg` page is **[inferred]** to carry the same value. The model receives one line (URL, mode, and whether the `NgHydration` mark is set, which it is not on the client route **[measured, same file]**) and explains it. The modern Angular pattern in a finding: the server route config (`app.routes.server.ts`, with `RenderMode.Server`, `RenderMode.Prerender` or `RenderMode.Client` per route), because it sets the render mode per route in one place. ### N24. Zoneless stale-view finder

- Prompt: "Why does the page still show the old status after the request finished?"
- How: the page agent reads the template node of the selected component in `ng.ɵgetSignalGraph`; that node's `debuggableFn` holds the whole class source (`research/raw/effect-writes.json`). A regex over that source finds assignments to a `this.<field>` inside a `subscribe(...)` callback, and `ng.isSignal(cmp.<field>)` tells a plain field from a signal. A hit on a plain field is a finding. On the zoneless counter fixture, with a temporary change `timer(300).subscribe(() => (this.plain = 'after'))` and `{{ plain }}` in the template, the DOM still showed `before` after 1.5 s while the instance held `after`, and an unrelated click then rendered `after` **[measured, `research/raw/stale-view-counter.json`, `13652e0`]**. The regex found `subscribe(() => (this.plain =` and `ng.isSignal(cmp.plain)` was false **[measured, same file]**.
- Finding text: names the modern Angular pattern, which is to assign a signal, or to use `toSignal`, `rxResource` or `httpResource`, and says why: in a zoneless app nothing schedules change detection after a plain field write that happens outside it, so the template is not rendered until something else triggers a cycle. The cause is **[inferred from the zoneless scheduler; the effect is measured]**. No code for the app (Lars's ruling of 2026-10-12, section 8).
- Limits: writes through a helper method, through another object, or in minified code are not seen **[inferred]**. Whether the template reads the field is not checked by the regex; the finding is worded as "the template may show a stale value" **[inferred design]**. The insurance portal has no such case: its `subscribe` callbacks write only signals (for example `this.loaded.set(true)`), never a plain field **[measured by reading the portal source at `cc9ce25`, `research/13-portal-legacy-audit.md`, "Not flagged"]**.
- Adds over Angular DevTools: its property view reads the instance, so it shows the new value next to a page that shows the old one, with no reason **[inferred]**. N24 names the write and the cause.
- Not an RxJS flag: RxJS is not legacy (`research/12` X1). The finding is about a plain field written outside change detection; the same write in a `setTimeout` or a `Promise` callback has the same effect **[inferred]**, though the regex looks for `subscribe` only.
- Deterministic part: the regex over `debuggableFn` and the `ng.isSignal` check are code, and so is the finding. The model receives the field name, the component and the matched source text capped at 200 characters (3.6), about 100 tokens **[inferred]**, never the class source that the template node's `debuggableFn` holds (05). Scanning every component on a page runs in a worker (3.7) **[inferred design]**.

## 6. Ecosystem features

Detection is by global, URL, DOM marker, directive class name, or token name in injector provider records, never by importing the tool's classes **[inferred, 04 section 0]**.

Reading values, not only detecting: a provider record holds the token and the provider definition, not the instance (`ProviderRecord`, 3.4), so the values this section reads come from one of two places **[inferred design]**:
- An instance the page already holds: a component field (from `ng.getComponent`) or a directive instance (from `ng.getDirectives`). This constructs nothing and is the first choice.
- `injector.get` with the token object from a provider record (2.2). For a `providedIn` token, the record appears only on the first `get`, which also creates the instance, so a later `get` on that record returns the existing instance. For a token listed in a `providers` array, the record exists before construction, so `get` can run the constructor **[inferred from `r3_injector.ts:345-362` and `:493`]**. The record alone does not tell the two apart, because both emit the class as the provider **[inferred from the same lines]**. So each `get` below says which case it relies on, and a `get` that can construct asks for a confirm first, as a write does (3.5).
- A third place, only in apps that add the opt-in export (2.2, Tier 2): a vetted package class or function from `globalThis`, under the safety rule there. The two places above stay the default.

### 6.1 NgRx Store and SignalStore

- Detection and data: a MAIN-world shim for `window.__REDUX_DEVTOOLS_EXTENSION__` installed at `document_start`. `provideStoreDevtools()` reads that global in a provider factory and then sends every action and state through it (`provide-store-devtools.ts:34-45`, `extension.ts:178-276` **[measured]**). `@angular-architects/ngrx-toolkit`'s `withDevtools` connects SignalStores through `window.__REDUX_DEVTOOLS_EXTENSION__.connect` and sends action names with state **[measured from source, 04 section 1.2]**, so the same shim should capture that traffic too **[inferred, 04 section 1.2]**. Caveat: the toolkit docs say `withDevtools` activates only after the user opens the "NgRx Signal Store" tab in Redux DevTools, so the shim may receive nothing until it imitates that step (spike S6). If the real Redux DevTools extension is installed, the shim forwards to it so both work **[inferred, spike S6]**.
- Without devtools providers: SignalStore state is readable by scanning store instances (found as component fields, section 6 intro; no `injector.get`) for the own symbol whose description is `STATE_SOURCE` (dev mode only, `state-source.ts:14-16` **[measured]**); polling gives sampled history. `STATE_SOURCE` is not exported from `@ngrx/signals`' public entry point, so this scan is Tier 1 (third-party) (2.2).
- Features:
  - "Explain this action trace": last N actions with state diffs; the model points to the action that changed the unexpected slice.
  - Anti-patterns from traces: actions that change nothing, action storms, non-serializable state.
  - Natural-language dispatch: the model proposes `{type, payload}` from observed action shapes; the developer confirms.
- Tier: 0 with the shim if the app has `provideStoreDevtools` or `withDevtools` (common in dev); Tier 1 (third-party) for the `STATE_SOURCE` scan; Tier 2 otherwise for exact history.
- With the opt-in export (2.2, `provideAiNgrxDevTools()` and the `@ngrx/signals` entry point): SignalStore state comes from the public `getState` instead of the `STATE_SOURCE` scan, and an app without `provideStoreDevtools` gets the global store's state from `Store.state` and its action stream from `ScannedActionsSubject` (from the moment the extension subscribes, with no earlier history). Tier 2 (app opt-in); the shim and the Tier 1 scan stay the default **[inferred design]**.

### 6.4 Analog.js

- Detection: only the `/_analog/` URLs identify Analog: server function calls to `/_analog/fn/:id`, and page endpoints under `/_analog/pages/`, or `/api/_analog/pages/` when the app has an API directory **[measured in Analog source, 04 section 2]**.
- `/@ng/component?c=` HMR requests and `/@vite/client` show only a Vite-based dev server (Angular CLI or Analog), so they do not identify Analog. Angular core builds the `/@ng/component?c=` URL (`packages/core/src/render3/hmr.ts:67` on 22.2.x), and the Angular CLI's Vite-based dev server answers it (`ANGULAR_COMPONENT_PREFIX = '/@ng/component'`, `angular-cli/packages/angular/build/src/tools/vite/middlewares/component-middleware.ts:12` on 22.0.x) **[measured in source]**. That the Angular CLI dev server also serves `/@vite/client` is **[inferred: Vite serves its client at that path, 04 section 2]**.
- Features: "route doctor" that explains why a URL 404s or which layout wraps a page, using the router state plus the file-route table from the root-provided `DEBUG_ROUTES` token (found by token name in provider records; `withDebugRoutes()` makes it visible without that lookup) **[inferred, 04 section 2]**. A root-provided token gets an injector record only when something first injects it (`r3_injector.ts:352-358`, 3.4) **[measured in source]**. `withDebugRoutes()` injects it only when its lazy debug page (`__analog/routes`) is opened: the route uses `loadComponent: () => import('./debug.page')` (`packages/router/src/lib/debug/index.ts:12`), and the only `inject(DEBUG_ROUTES)` in Analog's code is `injectDebugRoutes()` (`debug/routes.ts:35-37`), called from that page (`debug.page.ts:114`) **[measured in Analog source]**. So with `withDebugRoutes()` the token gets its record only after someone opens that page, unless app code calls `injectDebugRoutes()` itself, which `@analogjs/router` exports (`packages/router/src/index.ts:24`) **[measured in Analog source]**. Whether an Analog app injects `DEBUG_ROUTES` without it is open (S12). Reading the table needs `get` with the token from the record; `DEBUG_ROUTES` is a `providedIn: 'root'` token (04 section 2), so a record means the table was already built, and that `get` returns it without constructing anything **[inferred, section 6 intro]**. "Slow page" tracing from a page to its server function calls via network timing.
- The opt-in export (2.2) does not help here: `@analogjs/router` does not export `DEBUG_ROUTES` (2.2, "Not on the list").
- Tier 0 for network patterns; Tier 1 (third-party) for the `DEBUG_ROUTES` lookup by token name, which reads Analog's internal token through `ɵgetInjectorProviders`; opt-in for `withDebugRoutes()`.

### 6.5 RxAngular

- Detection: directive classes `RxLet`, `RxFor`, `RxIf` via `ng.getDirectives`; `RxState` instances found as component fields; `RxStrategyProvider` by token name **[names measured in source, 04 section 5; runtime detection inferred, because 04 ran nothing]**. - Features: show which blocks render with which strategy and recommend strategies from observed update frequency; read `RxState.get()` for state questions. No migration hints from `RxState` to signals: the extension does not suggest migrations (Lars's ruling of 2026-10-12, section 8).
- Where the values come from (section 6 intro): `RxState` from instances found as component fields, with no `injector.get`. Strategy names need `get` with the `RxStrategyProvider` token from a provider record. Whether that class is `providedIn: 'root'` was not checked (04 names it as a class only), so that `get` counts as able to construct it and asks for a confirm first **[inferred design]**.

Tier 2 (app opt-in); the Tier 1 (third-party) lookup stays the default **[inferred design]**.
- Caveat: RxAngular's peer range was Angular `^21` when checked, so 22.2 support is unverified **[measured peer range, 04 section 5]**. Lowest priority.
