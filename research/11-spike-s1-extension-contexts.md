# 11 - Spike S1: the Prompt API in each extension context

Question (feature proposals, section 3.1 and section 7, row S1): can a Manifest V3 extension use `LanguageModel` from each of its contexts, in Chrome Beta 156 and Edge Dev 157?

Status: **done.** Phase 1 measured API exposure in fresh profiles with no model on disk. Phase 2 measured `contextWindow` and one tool round trip per context on the standing Gemma 4 (Chrome Beta, port 9334) and Aion (Edge Dev, port 9335) instances; see "Phase 2" below.

Every claim is labelled **[measured]** (observed in a run recorded below) or **[inferred]**.

## Setup

- Extension: `spikes/s1-extension/` (retired in M009; evidence and archived notes live under `.project/archive/001-run-unrun-spikes/`). One shared probe, `probe.js`, runs in every context and records `typeof LanguageModel`, `typeof LanguageModelToolCall`, `typeof LanguageModelToolSuccess`, `isSecureContext`, `document.featurePolicy.allowsFeature('language-model')`, `LanguageModel.availability()` with no options and with the tool options (`expectedInputs` text + `tool-response`, `expectedOutputs` text + `tool-call`), and every error text. It calls `LanguageModel.create()` only when availability is `available`, so phase 1 could not start a download. The tool round trip follows `spikes/probes/probe6.js` (`callID` passed back in `LanguageModelToolSuccess`, two tools, each with one required parameter), with the tool names of `probe10.js` (`get_component_count`, `get_component_inputs`); phase 2 explains why the names changed.
- Each context writes its result to `chrome.storage.local` under its context name. Content scripts relay through the service worker (MAIN world -> `window.postMessage` -> isolated world -> `chrome.runtime.sendMessage` -> service worker); the offscreen document also relays, because it has no `chrome.storage`. `results.html` shows the whole store as JSON.
- Runner: `node spikes/s1-extension/run-s1.mjs ...` (retired in M009; evidence and archived notes live under `.project/archive/001-run-unrun-spikes/`). It writes `research/s1-results/<browser>-<model>.json`. Launch mode starts a fresh browser and deletes its profile afterwards; `--attach` uses a running instance, closes the tabs it opened and unloads the extension with `Extensions.uninstall`.
- Phase 1 ran an earlier revision of the extension: content scripts matched `<all_urls>` and the test page was `http://localhost:<p>/s1-test` from a server inside the runner. For phase 2 the content scripts match only `https://example.com/*` (the test page), so the probe globals stay out of other pages, and the load-time probes record exposure only. The runner then triggers the round trip in one context at a time over CDP (`s1RunRoundTrip`), so model sessions never run in parallel. A launch-mode run of the new revision gave the phase 1 values again **[unrecorded observation, Chrome Beta, 2026-10-12 01:59 UTC; no evidence file was kept, so treat it as unverified]**.
- Runs: Chrome Beta `156.0.8078.17` on port 9341, Edge Dev `157.0.4322.0` on port 9342, 2026-10-12 (the evidence files hold the last of several runs per browser; earlier runs differed only before the MAIN-world fix below), each a fresh profile under `.browsers/s1-<browser>-<port>` (deleted after the run), launched with the `--enable-features` lists from the brief plus `--enable-unsafe-extension-debugging --auto-open-devtools-for-tabs --window-size=1800,1100`. Evidence: `research/s1-results/chrome-fresh.json`, `research/s1-results/edge-fresh.json`.

## What this settles

- **The Prompt API, including the tool-use types, is exposed in all eight contexts in both browsers** **[measured]**. `LanguageModelToolCall` being a function everywhere shows `AIPromptAPIToolUse` reaches extension pages, the extension service worker, offscreen documents and both content-script worlds.
- **The DevTools panel, the side panel, the service worker and the offscreen document all get a usable `availability()`** (`downloadable`, the same answer as a normal tab) **[measured]**. The panel works because the DevTools frontend delegates `language-model` to it: `featurePolicy.allowsFeature('language-model')` is true there **[measured]**, which matches the `allow=` list in `ExtensionView.ts` described in 01 section 3.
- **The `devtools_page` is blocked by Permissions Policy**: `LanguageModel` exists, but `allowsFeature('language-model')` is false and `availability()` resolves to `unavailable` without throwing **[measured]**. Cause **[inferred]**: the DevTools frontend creates the hidden `devtools_page` iframe without the `allow=` list it gives panel iframes. Consequence for the design: never host a session in the `devtools_page`; it only registers the panel. This settles the "Unconfirmed" row in 01 section 3.
- **Content scripts get web-page semantics as expected**: same values as the page itself in both worlds **[measured]**. Whether the extension-only legacy parameters differ there was not checked.
- **Edge Dev 157 behaves like Chrome Beta 156 in every context** **[measured]**. This settles 01 section 3's Edge question for exposure; phase 2 shows Aion answering from those contexts.

## Findings on the way

- **`Extensions.loadUnpacked` works over `--remote-debugging-port`; the pipe is not needed** **[measured]**. It returned the extension id over the port in Chrome Beta 156 and Edge Dev 157, and over `--remote-debugging-pipe` in Chrome Beta 156 as well. It also loaded the extension **without** `--enable-unsafe-extension-debugging` in both browsers: the id came back and the extension's `sw.js` service-worker target appeared in `/json/list` **[measured, scratch test, fresh profiles on 9343 and 9344]**. The runner still passes the flag. Chromium source at tag `156.0.8078.17` agrees: `chrome/browser/devtools/chrome_devtools_session.cc` creates `ExtensionsHandler` with `allow_loading_extensions = (agent host type == browser)`, and `chrome/browser/devtools/protocol/extensions_handler.cc` checks only that value ("Method not available." otherwise); neither file tests for the pipe or the flag **[measured, source read]**. The protocol definition (`devtools-protocol` `pdl/domains/Extensions.pdl`) states no such condition either **[measured]**. Edge source is closed; Edge behaved the same **[measured]**. Phase 2 can therefore load the extension into the standing instances without relaunching them **[inferred here; measured in phase 2]**.
- `--load-extension` was not needed and not measured.
- The extension id is derived from the unpacked path, so it is `adkapcgoeebpdmbepbdjmbhfknkcllcc` in both browsers for this checkout **[measured]**.
- **A file listed in two content-script entries is injected only once per frame: here into the isolated world, whose entry is listed first.** With `probe.js` listed in both the isolated and the MAIN-world entry, the MAIN world got `cs-main.js` but no `probe.js` globals (`typeof s1Probe === 'undefined'`) **[measured, Chrome Beta 156]**. The runner therefore copies `probe.js` to `probe-main.js` on every run, and the MAIN-world entry lists that copy. For the real extension: give the page agent its own bundle file.
- `Extensions.extensionServer.onShowPanel` opened an extension panel in both branded browsers, not only in Chrome for Testing as the control-angular-devtools skill states **[measured]**. The runner keeps a fallback that clicks the DevTools tab titled `S1`; it was not needed.
- `chrome.sidePanel.open()` accepted a CDP-dispatched Enter key as the user gesture in both browsers, and `sidepanel.html` appeared as a `page` target **[measured]**.

What this settles:
- **A `LanguageModel` session with tools works in seven of the eight contexts in both browsers**: DevTools panel, side panel, service worker, offscreen document, both content-script worlds and an extension tab **[measured]**. The service worker needed no user activation, because the model was already `available` **[measured]**. The `devtools_page` is the only context that cannot create a session, and it fails with a clear `NotAllowedError` **[measured]**. These instances ran with the AI feature flags on; without them Edge drops `LanguageModel` from the page and the service worker (`20-built-in-ai-without-flags.md`, 2026-10-19).
- **Hosting context does not change the model's behaviour.** Within one browser, every context made the same tool call with the same arguments and used the same tokens (Aion 239 in all seven; Gemma 4 509-513) **[measured]**. Answer wording varied on Gemma 4 only.
- **Aion picked the wrong tool on this question in all seven contexts.** It called `get_component_count` with `scope: "app-counter"` and reported 42 as the count input **[measured]**. 00 records Aion answering the same question correctly with `probe10.js`. (Corrected: that Aion answer came from `spikes/probes/probe5.js` / `probe6.js` (00, "Edge Dev 157 results (Aion), measured"); `probe10.js` is the Gemma 4 run. That earlier Aion run used camelCase tool names, `getComponentCount` and `getComponentInputs` (`probe5.js:15-16`), so tool naming is another difference from this run.) This run's system prompt and tool result shape differ from that probe **[inferred as the likely cause, not isolated]**. This is answer quality, which is S4's subject, not an exposure problem.
- Reaching the contexts on instances started without `--auto-open-devtools-for-tabs`: CDP `Target.openDevTools({targetId})` opened an undocked DevTools window for the test tab in both browsers. That ran the `devtools_page`, and `onShowPanel` then showed the panel **[measured]**. No relaunch was needed. `Extensions.loadUnpacked` loaded the extension into both running instances, which were started without `--enable-unsafe-extension-debugging`. `Extensions.uninstall` removed it afterwards, and `Extensions.getExtensions` then returned an empty list on both ports **[measured]**.

### Finding: camelCase tool names crash Gemma 4's model process

- The first phase 2 run on Gemma 4 used `probe6.js`'s tool names `getComponentCount` / `getComponentInputs`, each with one required parameter. The DevTools panel, side panel and service worker each failed on the first `prompt()` with `UnknownError: An unknown error occurred: kErrorUnknown`. After the third failure, every later context reported `unavailable`, and `create()` threw `NotSupportedError: The model process crashed too many times for this version.` **[measured]**. Doctor then showed the `prompt_api_gemma4` use case as "Not Supported" and exited 1 **[measured, `research/s1-results/chrome-gemma4-crash-doctor.json`]**.
- Recovery: Chromium 156 disables the on-device model after 3 crashes without a successful response. The re-enable backoff is 1 minute at the third crash and doubles per further crash, up to 1 hour. A successful response resets the count (`on_device_model_access_controller.cc`; `GetOnDeviceModelCrashCountBeforeDisable() = 3`, base backoff 1 min, max 1 h in `optimization_guide_features.h`) **[measured, source read at tag 156.0.8078.17]**. About a minute later doctor passed again (exit 0) without a restart **[measured]**.
- Controlled pair in a normal page tab on the same instance: the doctor's one-tool canary named `get_component_count` passed, and the identical tool renamed `getComponentCount` failed with `kErrorUnknown` on the first prompt **[measured, `research/s1-results/chrome-gemma4-tool-name-pair.json`]**. The rename changes both case and underscores, so whether case alone or the missing underscores trigger it was not separated **[inferred: "camelCase" is the label, not the measurement]**. Each failure was followed by a success, so the crash count never reached 3 again. With the snake_case names, the full S1 round trip passed in all seven contexts.
- Consequence: 00's inference that a parameterless tool breaks Gemma 4 is confounded. Every failing probe there also used camelCase names, and every passing one used snake_case. The name alone reproduces the failure **[measured]**; 00's failing probes also had an empty schema, so that remains a possible second cause. Whether an empty schema also fails was not tested again. For the design: name tools in snake_case, and remember that each `kErrorUnknown` on Gemma 4 counts as a model crash; three in a row disable the Prompt API for the whole browser for at least a minute.
- Answered (2026-10-12, spike S11): the controlled test ran on the Gemma 4 instance (Chrome Beta 156.0.8078.17, GPU low tier), one fresh session per variant. `get_component_count` with a required parameter and with empty `properties`, and `getcomponentcount`, returned tool calls; `getComponentCount` and `Get_component_count` failed with `kErrorUnknown` **[measured, n=1 per variant, `research/raw/tool-name-matrix-gemma4-gpu.json`]**. An uppercase letter in the tool name is what fails; missing underscores and an empty `properties` schema do not **[measured, n=1 per variant; inferred that it generalises]**. The rule is now: tool names are lowercase (snake_case recommended for readability), and a tool with nothing to ask may take an empty `properties` schema (`docs/feature-proposals.md` 2.1). Gemma 4 on CPU, Nano, Aion and Phi-4-mini were not run on the matrix. A doctor run right after the matrix passed every canary, so its two crashes did not disable the model; a success resets the count (above) **[measured]**.
